# 이행 검토는 이렇게 확인한다

검토는 precision/recall 정답 작성과 다르다. **새 청크의 주소와 기존 참조를 안전하게 연결하기 위한 확인**이다. JSON을 편집하거나 544개 행을 하나씩 주석할 필요는 없다. 검토 결과를 아래 Markdown의 판정·메모 칸에 적는다. 메모 작성만으로 코드·골든셋·DB에 자동 반영되지는 않는다.

## 1. 먼저 확인할 파일과 작업량

| 순서 | 문서 | 실제 확인 단위 | 무엇을 판단하나 |
|---|---|---|---|
| 1 | [인용 이동 검토표](청킹_인용이동검토표_20261106.md) | 인용 11건. 모두 같은 문서·쪽의 단일 후보가 기계적으로 확인됨 | 원래 정답의 조건·예외·수행자가 새 청크에도 보존됐는가 |
| 2 | [주소 검토표](청킹_주소검토표_20261106.md) | **544개 행 → 64개 표** | 원본에서 표가 어떤 장·절·항에 속하며 실제 제목은 무엇인가 |
| 3 | [행동 단계 검토표](청킹_행동단계검토표_20261106.md) | **55개 행동 → 5개 근거 청크** | 저장 단계와 새 주소의 단계가 다를 때 어느 문맥을 따라야 하는가 |

55개는 추가 자동 점검에서 찾은 **검토 후보**다. 54개는 미지정→대응3으로 보완 가능성이 있는 경우이고, 1개는 기존 대응3과 주소 대응2가 충돌한다. 표 행이 다른 단계를 명시할 수도 있으므로 기존 데이터 오류로 확정하지 않는다. 단계 검토는 명확한 충돌 1개를 먼저 보고, 미지정 54개는 해당 4개 근거 청크를 묶어 확인하면 된다.

## 2. 주소 검토표: 표 하나를 확인하는 방법

1. 목록의 T01~T64를 눌러 상세로 이동한다. 문서명, PDF 쪽, 인쇄 쪽, 작업본 제목, 행 미리보기가 있다.
2. 해당 **원본 PDF의 PDF 쪽수**로 이동한다. 예: PDF 185쪽은 인쇄 175쪽이다. 두 숫자를 바꾸어 찾지 않는다. PDF 파일이 이 저장소에 있다는 뜻은 아니며 본인이 보유한 원본을 연다.
3. 표가 속한 장→로마 숫자 절→숫자 항목→질병 제목→한글 소절을 원본에서 따라간다. 같은 페이지 아래쪽의 다른 제목을 가져오지 않는다. 앞 페이지에서 이어지는 상위 제목도 확인한다.
4. 실제 표 제목도 확인한다. 작업본의 ‘후보 1’, ‘원본 이미지 대조’ 같은 말이 원문 제목인지 따로 구별한다. 원문에 제목이 없으면 없다고 메모하며 공식 제목을 지어내지 않는다.
5. 현재 주소가 원문과 일치하고 필요한 하위 소속까지 확인됐으면 `주소 맞음`. 틀리거나 상위 범위만 나와 있다면 `주소 수정`과 `확정 주소`를 쓴다. 배치가 불명확하거나 원본이 없으면 `원문 확인 불가`다.

입력 칸은 각 표에 이미 있다.

```text
- 판정: 주소 수정
- 확정 주소: (원본에서 확인한 전체 제목 경로)
- 근거: 경기도 가이드북 PDF ○쪽 / 인쇄 ○쪽, 표 위 소제목 ○○
- 메모: 표가 앞 페이지에서 이어짐 / 제목 없음 / 변환 순서가 뒤집힘 등
```

`주소 맞음`도 `확정 주소`를 채우면 어느 깊이까지 확인했는지 알 수 있다. 모르면 미검토로 남기고 임의로 승인하지 않는다. 같은 표의 모든 행을 반복 검수하지 않아도 된다. 단, 표 내부에 서로 다른 질병·단계가 나뉘어 있으면 그 구분은 메모한다.

현재 `context_verified=False`는 **틀렸다는 판정이 아니라 캡션으로 정확한 위치를 확정하지 못했다는 표시**다. 일부 주소는 이미 맞을 수 있다. 이 검토에서는 맞는 주소를 다시 작성하려고 불필요하게 바꾸지 않는다.

본문 Markdown 링크는 해당 PDF 페이지 구분자 줄을 연다. PDF 배치를 대신하는 정답이 아니므로 표·소제목 순서가 이상하면 원본 PDF를 우선한다. 일부 편집기에서 줄 번호 링크가 열리지 않으면 파일을 연 뒤 `## PDF 185페이지`처럼 검색한다.

## 3. 인용 이동 검토표: 정답을 새로 작성하는 작업이 아니다

- 각 항목에서 `이전 ID`, `발췌`, `새 후보`, `새 주소`, `새 청크 전체 내용`을 함께 본다.
- 11건 모두 동일 문서·PDF 쪽에서 발췌가 포함된 후보가 **하나씩** 나왔다. 재검색이나 후보 ID 계산은 이미 끝났다.
- 원래 발췌의 의미와 조건·예외가 새 청크에서도 유지됐다면 `동일 근거로 이동`, 아니면 `다른 근거라 보류`라고 적는다. 한 정답이 쪼개진 여러 청크를 필요로 하면 그 사실을 메모한다.
- 예: C01은 교육부 PDF 53쪽의 `p0053:b01`에서 `p0053:b02`로 이동하는 후보다. 같은 문자열을 찾았다는 사실과 정답 맥락이 온전히 남았다는 판단을 구별한다.
- 인용 11건은 **서로 다른 원본 페이지 6쪽**에 있다. 같은 페이지는 함께 확인할 수 있다. 정답의 문구·조건을 모델 출력에 맞추어 고치지 않는다.

## 4. 행동 단계 검토표: 주소의 단계와 행동의 단계를 구별한다

새 주소가 대응2인데 행 안에서 ‘대응3으로 확대’ 등을 명시할 수 있다. 따라서 자동 후보를 그대로 정답으로 쓰지 않는다. 표의 열 머리글·행의 단계/조건·상위 제목을 함께 확인한다.

- 기존 유지: 행 자체의 단계가 명시되어 있거나 단계 불명이라 기존 미지정이 타당함.
- 단계 수정: 원문에서 기존 단계가 틀리거나 누락된 것이 확인됨. 메모에 수정할 단계와 원문 근거를 적음.
- 근거 부족 보류: 원본 없이 결정할 수 없음.

특히 `moe_school_manual_v3:p0060:a05`(능동감시를 전체 학급으로 확대)는 저장값 대응3 / 상위 주소 대응2로 충돌한다. 표의 단계·적용 조건을 확인하기 전에는 오류로 확정하거나 대응2로 낮추지 않는다.

## 5. 결과를 반영하는 방법

검토표에 판정과 메모를 적고, 완료한 T번호·C번호·행동 근거 청크를 알려주면 된다. 전체 64개를 한 번에 끝낼 필요 없이 일부씩 확인할 수 있다.

반영 단계에서는 다음을 구분한다: 주소 보정은 검증 근거를 가진 청킹 규칙/보정 데이터로, 인용 이동은 새 데이터 전용 골든 참조로, 행동 단계는 원문 근거가 있는 정규화 데이터로 반영한다. 그 후 회귀 검증을 다시 수행하고 공유 DB 적용을 진행한다. 현재 메모를 적는 것만으로 DB가 변경되거나 검증 완료로 처리되지는 않는다.

## 생성·검증 근거

입력: `data/interim/school/chunking_v2_20261105T223223_186130Z/`의 저장 산출물과 이전 승인 행동. 재생성 도구: `chunking_review_pack.py`. 생성 문서에는 원문의 표 행 미리보기가 있으므로 저장소의 자료 공유 범위를 따른다.

```powershell
.venv/Scripts/python.exe -X utf8 notebooks/school/평가결과/chunking_review_pack.py --artifacts data/interim/school/chunking_v2_20261105T223223_186130Z --out-dir <새_출력폴더>
```

기존 검토 문서를 덮어쓰지 않는다. 재생성이 필요하면 존재하는 새 출력 폴더를 지정한다. 이번 문서 생성은 승인·정답 확정·DB 변경·성능 재평가를 수행하지 않았다.
