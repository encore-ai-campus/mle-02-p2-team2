# 발표 쪽별 입력 원고 (미리캔버스 40쪽 캔버스 기준, 2026-11-07)

- 대상 캔버스: 「교육시설 감염병 근거 Q&A 발표 앞부분- 복사 for Claude」(40쪽, 읽기만 했고 **수정하지 않았다**). 연결된 편집 도구는 승우 님이 만든 기존 디자인의 쪽 추가·수정을 허용하지 않아서, 이 문서를 보고 직접 입력하는 방식이다.
- 구성 근거: [슬라이드 구성안 v4](발표_슬라이드_구성_제안_20261107.md), 내용 근거: [로직 부품 정리](질문에서_답변까지_로직부품_정리_20261107.md). 수치 출처는 쪽마다 적었다.
- 기존 1~12쪽(표지·목차·배경·개요·구조도·스키마)은 건드리지 않는다.

## 0. 입력 규칙

### 0-1. 템플릿 쪽 번호 (40쪽 캔버스 기준, 구성안 v4보다 +2)

| 번호 | 레이아웃 | 이 문서의 약칭 |
|---|---|---|
| 5 | 카드 3장(번호·키워드·본문), 기존 배경 쪽 | **T5** (22쪽에만 사용) |
| 28 | 아이콘 4칸(2×2) | **T4** |
| 29 | 아이콘 3칸(원형 아이콘) | **T3** |
| 30 | 아이콘 6칸(카드 2열×3행) | **T6** |
| 31 | 이미지 + 수치 2개 | **TI** |
| 32 | 이미지 3칸 | (미사용) |
| 33 | 게이지 2개 + 꺾은선 차트 | **TG** |
| 34 | 4×4 표 + 레이더 차트 | (미사용) |
| 35 | 5열×5행 표 | **TB** |
| 36 | 순환 4단계 | (미사용) |
| 37 | 타임라인 4단계 | **TL** |
| 38 | 역할분담(4명 카드) | 그대로 사용(3명으로) |

- 새 쪽은 위 템플릿 쪽을 **복제**해서 만든다. 복제 후 맨 위 작은 글(예: "아이콘 핵심을 전달하는 레이아웃")을 반드시 **구분 이름**(예: "기술 | Skills")으로 바꾼다.
- 이미 제목만 있는 기존 쪽(17·18·22·24·26·27)은 **템플릿을 복제한 뒤 같은 제목을 넣고**, 빈 제목 쪽을 대신하면 된다(지우는 것은 승우 님 판단).
- 13~15쪽은 스키마 쪽 복사본이라 내용이 없다. 아래 새 쪽으로 대체한다(지울지는 승우 님 판단).

### 0-2. 글자 수 한도 (글자 폭 ≈ 글자 크기로 추정한 값. 입력 후 넘침을 눈으로 확인)

| 칸 | 한도 |
|---|---|
| 제목(64px) | **15자**, 한 줄. 더 길면 상자 가로를 늘린다(27쪽이 이미 1,228px) |
| 구분 이름(32px) | 21자 |
| T4 키워드(40px) / 본문(26.7px) | 10자 / 3줄×15자 (≈40자) |
| T3 키워드 / 본문 | **6자** / 3줄×15자 |
| T5 키워드(40px) / 본문(26.7px) | 11자 / 한 줄 16자, **3~4줄(≈50자) 권장** |
| T6 키워드(32px) / 본문 | 17자 / 점(·)으로 시작하는 2줄, 줄당 21자 |
| TI 제목 / 본문 / 수치 / 라벨 | 19자 / 약 150자 / 4자(80px) / 7자 |
| TG 제목 / 설명 | 13자 / 32자. 게이지 숫자·글, 차트 값은 편집 화면에서 직접 |
| TB 머리글 / 칸 | 10자 / 한 줄 11자, **2줄 22자**까지 |
| TL 단계 이름 / 본문 | 6자 / 3줄×15자 |

- 한도를 넘는 내용은 슬라이드에 넣지 않고 **발표 대본**에 둔다. 아래 쪽마다 "발표 대본"이 그 자리다.
- 쪽에 없는 칸(예: T3의 오른쪽 위 괄호 글)은 비워 두지 말고 아래 원고대로 넣거나 지운다.

### 0-3. 표시 약속

- **[확인]** 승우 님이 정해야 하거나 측정 전이라 비워 둔 값. 슬라이드에 그대로 쓰지 않는다.
- **(1인)** 사람 확인 전 단독 채점·주석 값. 각주에 "1인 채점"을 꼭 쓴다.

### 0-4. 쪽마다 쓰는 형식과 용어 풀이 (대본이 불친절하다는 지적 반영)

쪽마다 다음 순서로 쓴다. **기술·시연·발전 경과·한계·발전 방향 쪽에 적용했다.** (1~12쪽과 38쪽 카드 문구는 기존 그대로)

1. 이 쪽에서 청중이 가져갈 **한 문장**
2. 슬라이드에 넣을 글(칸별)
3. **바뀐 것 / 왜 그런지**를 표로(숫자만 있는 쪽에는 원인을 반드시 붙인다)
4. **발표 대본**: 줄임말 없이 그대로 읽을 수 있는 문장으로. 용어는 처음 나올 때 한 번 풀어 말한다
5. 질문이 나올 때 쓸 용어 풀이·한계·근거 파일

| 용어 | 대본에서 이렇게 말한다 |
|---|---|
| 청킹·청크 | 원문 PDF를 검색할 수 있는 조각으로 자르는 일 / 그 조각 |
| Hit@k | 정답이 들어 있는 조각이 검색 결과 상위 k개 안에 있는 질문 수 |
| MRR@10 | 정답이 처음 나온 순위의 역수를 질문마다 구해 평균한 값. 1에 가까울수록 정답이 위쪽 |
| hybrid 검색 | 단어 기반(fulltext)과 vector를 합친 검색 |
| 골든셋 | 정답 근거를 미리 적어 둔 평가용 질문 40개(정답 청크가 있는 34개로 검색을 잼) |
| 정밀도·재현율 | 찾은 것 중 맞은 비율 / 있어야 할 것 중 찾은 비율 |

## 1. 최종 쪽 순서 (전체 44쪽, N10·N4·N17 제외)

`기존`은 이미 있는 쪽, `＋`는 새로 만드는 쪽이다. 번호는 40쪽 캔버스 기준이고 새 쪽을 끼우면 뒤 번호가 밀린다.

| 장 | 순서 |
|---|---|
| 01~02 | 1 표지 · 2 목차 · 3~7 배경 · 8~9 개요 (기존, 그대로) |
| 03 구조 | 10 구분 · 11 구조도(전체 한 쪽, 신규 그림) · 12 스키마(기존 화면에 노드 수 추가) · **＋N1** LLM은 세 곳만 (T3) |
| 04 기술 | 16 구분 · **17**(T L) 원문이 지식그래프가 되기까지 · **＋N2** 질문 이해 (T6) · **＋N3** 찾기 (T4) · **＋N5** 판단형 답변 (T4) · **＋N6** 줄 단위 검사 (T6) · **18**(TB) 사용 기술 |
| 05 시연 | 19 구분 · **＋N7** 개선 전과 후 (TB) · **＋N8** 화면 (TI) · 20 (기존, 쿼리·cypher 시각화) |
| 06 발전 경과 | 21 구분 · **22**(T5) 개요 · **＋N9** 어떻게 쟀나 (TB) · [청킹/적재] **＋N11** (TB) · **＋N12** (TG) · [검색] **＋N13** (TG) · **＋N14** (TG) · **＋N15** (그래프+숫자 카드) · [답변] **＋N16** (TB, 6번의 개선) · **＋N20** (2026 지침 전/후) · **＋N18** (TB) |
| 07 한계·기대 | 23 구분 · **24**(T4) 한계 · **＋N19** 기대 효과 (T4) |
| 08 발전 방향 | 25 구분 · **26**(T4) 질병 확대 · **27**(T3) 서비스 자체 개선 |
| 마무리 | **38** 역할분담(3명) · 39 Q&A · 40 감사 |

- 템플릿 원본 28~37쪽은 복제한 뒤 쓰지 않으면 지우거나 맨 뒤로 보내면 된다.
- 44쪽은 20분에 많다. **발표 모드에서 숨길 쪽**(N10·N4·N17은 쓰지 않음): 20, 38(→ 42쪽). N16은 답변 품질 6단계 개선이라 이제 숨기지 않는다. 40쪽 이하로 줄이려면 27, N19, N18 중 둘을 더 숨긴다. 시간 배분은 [구성안 v4 3장](발표_슬라이드_구성_제안_20261107.md)의 20분 표를 따른다.

## 2. 03 구조

### 11 — 구조도 (전체 구조도 한 쪽, 12쪽은 기존 스키마 쪽 그대로)

그림 파일: [구조도_최종_20261108.png](../20261108/구조도_최종_20261108.png) 하나만 쓴다. 구조 장은 **11쪽(전체 구조도) → 12쪽(기존 스키마 쪽, 지금 보이는 그대로) → N1(LLM은 세 곳만)** 순서다. 구조도를 위·아래로 나누지 않는다.

- 제목은 기존 그대로, 구분 이름 `구조 | Structure`.
- 그림이 세로로 길어서 쪽 높이에 맞추면 글자가 작다. 발표 대본이 흐름을 말로 짚으니, 그림 옆에 **번호 원 ①~⑦**만 올리고 순서대로 짚는다.
- 12쪽 스키마 쪽은 이번에 건드리지 않는다.

| 번호 | 그림 위치 | 짚는 말 |
|---|---|---|
| ① | 질문 이해(LLM 라우터) | 질병·의도·하위 질문·상황·확인 항목을 뽑는다 |
| ② | 지원 범위 확인, 일반 LLM | 11개 질병 질문이 아니면 일반 안내 |
| ③ | 판단 기준 원문 조회(오른쪽 점선) | Tool과 동시에 원문을 가져온다 |
| ④ | Tool 선택과 네 Tool | 주 Tool, 동반 호출, 최대 3회 |
| ⑤ | 근거 검증·합치기, 추가 탐색 | 원문 대조, 부족하면 다시 Tool로 |
| ⑥ | 근거 선별(LLM) | 36장 중 10개, 2026 지침 우선 |
| ⑦ | 충분한가? → 답변 / 부족 안내 | 줄 검사, 모르면 모른다고 쓴다 |

**한 문장:** "질문 하나가 이해, 검색, 선별, 답변으로 흐르고, 근거는 코드가 검증하며 LLM은 세 곳에서만 일한다."

**발표 대본** (약 2분 30초)

1. "서비스 전체 흐름입니다. 위에서 아래로 한 번 따라가겠습니다. 점선 박스는 갈림길 판단이고, 점선 화살표는 동시에 실행되는 길입니다."
2. "질문이 들어오면 LLM 라우터가 질문을 이해합니다. 질병 이름과 별칭, 가장 알고 싶은 의도와 곁들여 알아야 할 의도, 의도별 하위 질문, 질병·인원·질문한 사람의 역할 같은 상황, 그리고 꼭 확인해야 할 항목을 정해진 형식으로 뽑습니다."
3. "다음은 우리가 지원하는 업무와 질병 11개에 관한 질문인지 봅니다. 아니면 DB나 Tool을 쓰지 않고 일반 대화나 범위 안내로 끝납니다."
4. "범위 안이면 두 가지가 동시에 시작합니다. 오른쪽 점선은 판단 기준 원문 조회입니다. 신고 대상 목록, 급수, 유행의심 기준, 조문과 벌칙, 역할 표를 사용자가 묻지 않아도 직접 가져옵니다. 판단에 꼭 필요한 기준이기 때문입니다."
5. "동시에 Tool을 고릅니다. Tool은 네 개입니다. 질병 정보를 찾는 Disease, 학교 행동을 찾는 SchoolAction, 법령·신고 근거를 찾는 Tool, 문서끼리 비교하는 복합 관계 검색이고, 모두 공통 Neo4j 지식그래프를 읽기만 하며 허용된 문서 안에서만 찾습니다. 가장 중요한 Tool을 주 Tool로 정하고, 질문에 11개 질병 이름이 있으면 Disease를 함께 부릅니다. 주 Tool이 근거를 못 찾으면 SchoolAction으로 넘기고, 호출은 전체 최대 세 번입니다."
6. "찾아온 근거는 먼저 원문과 허용 문서를 다시 확인해서 합치고, 허용된 문서나 쪽수 밖의 근거, 다른 질병이나 다른 조치에 관한 근거는 이 단계에서 제외합니다. 부족하면 다시 Tool로 돌아가고, 충분하면 두 번째 LLM이 근거를 고릅니다. 카드 최대 36장 중 번호로만 최대 10개를 고릅니다. 질문에 직접 답하는 근거, 적용 조건, 질문의 전제를 바로잡는 근거를 고르고, 핵심 구절은 코드가 원문과 대조합니다. 근거마다 판본도 표시해서 학교 문서와 2026 지침이 다르면 2026 지침을 앞에 둡니다. 판단 기준 원문은 이 단계에서 합류해 항상 남깁니다."
7. "근거가 모든 하위 질문에 답하는지 판정합니다. 충분하면 세 번째 LLM이 결론, 상황 판단, 할 일, 신고·법적 사항 순서로 답변을 쓰고, 줄마다 번호, 숫자, 주체, 강한 표현을 코드가 검사합니다. 일부만 답하거나 부족하면 확인하지 못한 부분을 밝히고, 근거에 없는 내용은 만들지 않습니다."
8. "정리하면 LLM은 질문 이해, 근거 선별, 답변 작성 세 곳에서만 일하고, 나머지는 DB 조회와 코드 검증입니다."

**질문이 나오면**

- 동반 호출은 공통 계약의 "기본 1개 Tool"과 다르다(팀에 공유, 합의 필요). 질병 Tool 수정은 송수림 님 파일이고 팀장 승인 하에 했다. 근거: N20, 답변 품질 개선과정 5·6장.
- 점수표·번갈아 뽑기(구 N4)는 발표에서 다루지 않는다. 질문이 나오면: 안전장치로 거른 후보를 사람이 만든 규칙 점수(핵심어·역할·단계·질병 일치)로 줄이고, 한 역할·문서가 상위를 독차지하지 않게 번갈아 16개를 남긴다. 의미를 판정하는 것이 아니라 줄이는 용도다. 그 결과가 그림의 "카드 최대 36장 → 최대 10개"의 입력이다.
- 근거 선별 상한 10은 사례를 보며 올린 값이고 상한끼리 비교한 실험은 없다.
- **[확인]** 그림의 "일반 LLM" 상자가 라우터와 별개의 LLM 호출인지 확인해 주세요. 코드상 라우터가 범위 밖 안내 문장을 함께 내므로 추가 호출이 아닐 가능성이 높지만 확인하지 못했다. 별개 호출이면 "질문당 3회"를 "범위 밖은 +1회"로 고친다.
- 그림의 질병 11개는 DB의 Disease 노드 수이고 24쪽(한계)·26쪽(발전 방향)의 11종과 같다.

**그림과 이전 원고의 다른 점**

| 구조도의 내용 | 이전 원고 | 고친 곳 |
|---|---|---|
| 지원 범위(11개 질병) 판단과 일반 LLM | N2는 "범위 밖은 검색 없이 안내"만 | 이 쪽, N2 |
| Tool이 네 개이고 동반 호출·넘겨받기·최대 3회 | N3 "네 갈래"와 겹침 | 이 쪽, N3 |

나눈 이유(스키마 설명서 기록):
1. **원문을 잃지 않으려고.** 같은 행동도 문서마다 표현·단계·강도가 다르다. 한 노드로 합치면 원문의 차이가 사라진다. 그래서 행동은 문서·위치별로 따로 두고(같은 행동이 여러 단계에 나오면 단계별로 별도 노드), 하나로 묶는 일은 이름표가 맡는다.
2. **문서가 달라도 같은 종류를 함께 찾으려고.** 두 문서의 "보호자 연락"을 개념으로 이으면 한 번에 가져올 수 있다.
3. **헷갈리면 안 되는 행동을 구분하려고.** 교육청 보고, 보건소 법정 신고, 방역당국 협조는 법적 의미가 다르므로 서로 다른 개념으로 둔다. "신고 정확성"을 지키는 장치다.
4. **표현을 고정하려고.** 개념은 사전으로 정해 둔 목록 안에서만 고르게 해서, 없는 개념을 만들지 못한다. 맞는 개념이 없으면 후보로 표시해 사람이 검수한다.

- **"검색은 오히려 좋아졌다"의 한계(질문이 나오면):** 정답 인용 21~22 → 27~29는 청킹 v4.1을 쓴 상태에서 검색 방식을 바꾼 값이다. v1 청크에 현재 검색을 적용해 비교한 실험은 하지 않았다. 그래서 "검색 개선이 청킹 손실을 만회했다"는 순서상 비교이지 같은 조건의 인과 증명이 아니다. 원시 Hit@10도 현재 검색(두 질의, 22)이 v1(단일 질의, 23)보다 낮다. 올라간 것은 후보를 넓게 가져온 뒤(Hit@30 31/34) LLM이 필요한 근거를 고른 최종 인용이다.
- 용어 풀이(질문이 나올 때): **Hit@10** = 정답이 들어 있는 조각이 검색 결과 상위 10개 안에 있는 질문 수. **MRR@10** = 정답이 처음 나온 순위의 역수를 질문마다 구해 평균한 값(1에 가까울수록 정답이 위에 있음). **80자 미만 청크** = 너무 짧아 누가·언제 같은 맥락이 없는 조각.
- 한계: 80자 미만 값은 v4.1에서 미집계. v1 본문 청크 367은 본문 기준이라 전체 청크 수(v1 1,139 → v3 1,922 → v4 1,339 → v4.1 1,289)와 다르다. 골든은 개발 중 본 문항이고, 청킹이 맥락을 잘 담았는지는 직접 재는 지표가 없어 검색 순위로 간접 확인한 것이다.
- 근거: [청킹 troubleshooting](../20261106/청킹_troubleshooting_20261106.md) 1~5장(v1 문제), [청킹 v4 기록](../20261106/청킹v4_항목묶기_재이행_20261106.md) 1·2장, [청킹 검수 수정 로그](../20261106/청킹_검수반영_수정로그_20261106.md), [현재 구조 Hit/MRR 결과](검색순위_HitMRR_현재구조_20261107.md)의 A행.

#### N14 — 넓게 찾기 단계별 변화 그래프 (정답 인용 기준, 11/07 측정 + 11/08 순위 보조)

게이지는 쓰지 않는다. 쪽 전체를 **하나의 꺾은선 그래프**로 쓴다. 이 쪽의 주인공은 **정답 인용**이다. 질의 1개 → 2개 비교용 상위 k 순위(Hit@k)는 슬라이드에 올리지 않고 대본·질문 대비에만 둔다. 차트 크기·위치는 자유롭게 조정한다.

| 단계(가로축) | 정답 1개 이상 인용 (/34) | 정답 청크 회수율 (/64) | 정답을 전부 인용 (/34) |
|---|---|---|---|
| 개선 전 (규칙 점수·문턱, 질문 1개) | 65% (22) | 45% (29) | 41% (14) |
| ① 질문 2개 + 문턱 제거 | 74% (25) | 58% (37) | 44% (15) |
| ② 인용 후보 완화 + 후보 30개 | **91% (31)** | **66% (42)** | **56% (19)** |

- 세 선: 정답 1개 이상 인용(강조색, 가장 굵게) / 정답 청크 회수율 / 정답 전부 인용. 선 끝에 값 라벨(91%, 66%, 56%)을 붙인다.
- 그래프 옆 말풍선(또는 아래 한 줄): "대가: 문항당 인용 9 → 12 → 19개, 정밀도 하한 0.093 → 0.066". 정밀도는 다음 쪽(근거 선별)에서 되찾는다는 점을 같이 말한다.
- 모두 **같은 조건**(메인 끝까지, 근거 선별 전, 같은 34문항 골든)이라 단계끼리 비교할 수 있다. 근거 선별을 켠 값(27~29)은 이 쪽에 넣지 않고 N13에서 보인다.
- 각주(직접 추가): "근거 선별 전 출력 기준. 골든 34문항은 개발 중 본 문항. 정밀도 하한은 골든이 대표 근거만 적어 실제보다 낮은 값."
- 숫자 출처: [총정리 4-2장](발표용_전체과정_검색품질_총정리_20261107.md)과 [근거 재순위 기록](근거재순위_스트리밍_20261107.md)의 v5, 넓게 찾기 v1, 넓게 찾기 v2 행(선별 없음).

**한 문장:** "질문을 두 개로 찾고 후보를 넓히자 정답 인용이 22개에서 31개로 늘었지만, 인용이 너무 많아졌다."

**발표 대본**

1. "검색 품질의 두 번째 개선인 넓게 찾기입니다. 원래 질문 하나로만 찾던 것을, 문서 용어로 바꾼 질문까지 두 개로 찾도록 바꿨습니다. 그리고 점수가 낮다고 후보를 걸러내던 문턱을 없앴습니다."
2. "그래프의 가로축이 세 단계이고, 선은 정답 근거를 하나 이상 인용한 질문 비율, 정답 청크를 인용에 담은 비율, 정답을 전부 인용한 질문 비율입니다. 모두 근거 선별을 하기 전 출력 기준입니다."
3. "질문을 두 개로 찾고 문턱을 없앴더니 정답 인용이 22개에서 25개가 됐습니다. 이어서 인용 후보를 걸러내던 규칙을 완화하고 후보를 30개까지 넓혔더니 34개 중 31개가 됐습니다. 정답 근거를 하나라도 인용한 질문이 65%에서 91%가 된 것입니다."
4. "대가도 있습니다. 문항당 인용이 9개에서 19개로 늘었고, 인용 중 정답인 비율인 정밀도는 낮아졌습니다. 많이 담았지만 필요한 것만 담은 것은 아니라서, 다음 단계인 근거 선별이 필요해졌습니다."
5. "참고로 검색 결과의 순위만 따로 보면, 같은 데이터에서 질문 두 개로 찾을 때 상위 10개 안에 정답이 있는 질문이 20개에서 22개로 늘었고, 후보를 30개까지 보면 31개입니다. 다만 상위 5개 안은 16개에서 14개로 약간 줄어서, 맨 위로 올리는 일은 뒤 단계가 맡습니다."

**질문이 나오면**

- 이 쪽의 세 선은 최종 출력 기준(메인 끝까지, 근거 선별 전)이다. 5번 대본의 순위 값(Hit@k)은 Tool이 고르기 전의 원시 검색 순위로, 대상이 달라서 같은 그래프에 섞지 않는다.
- 원시 순위(11/08, 데이터 v4.1 고정, 질문 1개 → 2개): Hit@1 7→6, Hit@3 11→12, Hit@5 16→14, Hit@10 20→22, Hit@30 (2개만) 31, MRR 0.312→0.303. 질문 1개 방식은 상위 10개까지만 기록돼 k=20·30 값이 없다. k=1·3·20은 문항별 첫 정답 순위 표([측정 결과](검색순위_HitMRR_현재구조_20261107.md))에서 센 값이다.
- 슬라이드에 쓰지 않는 값: Tool 출력 순서(C) Hit@10 25/34·MRR 0.473은 인용 목록이 길어(중앙값 19개) 순위가 쉽게 높아지므로 다른 값과 나란히 두지 않는다. LLM 선별 뒤 순위는 재지 않았다.
- 단계 ②는 인용 후보 완화·후보 30개·훑기 상위 6을 함께 바꾼 것이라, 각각의 효과는 나눠 재지 않았다.
- 한계: S-Q10·S-A03은 두 방식 모두 정답이 없다.
- 근거: [측정 결과](검색순위_HitMRR_현재구조_20261107.md)의 A·B행, 총정리 4-2장.

#### N15 — 질문 이해가 찾기를 넓힌다 (숨기지 않음, 정확도 그래프 + 찾기 효과 숫자 3개)

제목 `질문 이해가 찾기를 넓힌다`(12자) / 구분 이름 `발전 경과 | 검색 품질` / 소제목 `규칙 분류기 → LLM 라우터`

템플릿 칸에 맞추지 않고 쪽을 **왼쪽 그래프 + 오른쪽 큰 숫자 카드 3개**로 나눈다(T4 같은 아이콘 칸은 쓰지 않아도 된다). 그래프와 카드의 비율은 읽히는 쪽으로 조정한다.

**왼쪽: 질문 이해 정확도 (질문 종류를 올바르게 분류한 문항 수) — 규칙 분류기 vs LLM, 질문셋별 막대 비교**

| 질문 묶음 (슬라이드에 쓰는 이름) | 규칙 분류기 | LLM (현재) |
|---|---|---|
| 일상 표현 (20) | 9~10 | 20 (*) |
| 교직원이 실제로 물을 법한 질문 (15) | 15 | 15 |
| 새 질문 1차 (20) | 12 | 20 (**) |
| **한 번도 안 본 새 질문 (16)** | 11 | **15** |

- 강조는 마지막 묶음이다. "한 번도 안 본 새 질문"은 개발하면서 규칙·프롬프트를 고칠 때 보지 않고 따로 빼 둔 시험용 질문이다(전문 용어로는 홀드아웃). 슬라이드에는 "홀드아웃"이라는 말을 쓰지 않는다.
- 막대 옆에 (*) "프롬프트를 쓰기 전에 본 문항이라 과대평가", (**) "기대값 3개를 결과를 본 뒤 고침"을 작게 쓴다. 믿을 수 있는 값은 마지막 묶음의 15/16이다.
- 골든 40문항은 규칙도 40/40이라 그래프에서 뺐다(규칙을 이 골든에 맞춰 만들어서 비교가 안 된다).

**오른쪽: 이 질문 이해가 찾는 일을 어떻게 넓혔나 (숫자 카드 3개)**

| 카드 | 큰 숫자 | 한 줄 설명 |
|---|---|---|
| 1. 일상어를 문서 용어로 | **60위 → 6~10위** | 예시 질문 상자를 카드 아래에 붙인다(아래). 신고 대상 법정감염병 8종 목록을 찾는 순위 |
| 2. 질문을 두 개로 찾기 | **20 → 22** (상위 10개), **31** (후보 30개) | 34문항 중 정답이 순위 안에 든 문항 수. 질문이 두 개가 되면서 후보가 넓어짐 |
| 3. 맞는 Tool로 | **근거 없음 → 답함** | 신고 의무 질문을 학교 행동 + 법령으로 보냄. 정답 인용 21 → 22, 상태 일치 38 → 39 |

**카드 1 아래 예시 상자 (그대로 입력)**

- 사용자 질문: "성홍열도 학교장이 보건소에 신고해야 하나요?"
- 이 말로 그대로 찾으면: 신고 대상 8종 목록이 **60위** (후보 60개 중 꼴찌)
- 라우터가 바꾼 문서 용어 문장: "학교장이 신고해야 하는 법정감염병 종류" → **10위**, "신고가 필요한 법정감염병 종류 신고방법 법적근거" → **6위**
- 한 줄 풀이: 병명을 넣은 말로는 목록형 근거가 안 잡히고, 문서에 쓰인 말로 바꾸면 잡힌다.

- 각주(직접 추가): "질문셋과 기대값은 Claude가 작성, 팀 검수 전. 1번은 사례 1건, 2번은 원시 검색 순위(데이터 고정), 3번은 골든 34문항."

**한 문장:** "질문을 LLM이 이해해 문서 용어로 풀어 주자, 처음 보는 질문도 더 잘 분류하고 찾을 근거도 넓어졌다."

**발표 대본**

1. "검색 품질에서 질문 이해를 빼놓을 수 없습니다. 처음에는 규칙으로 질문의 종류를 가렸는데, LLM으로 바꿨습니다."
2. "왼쪽이 질문을 올바르게 분류한 문항 수입니다. 시험 문제를 미리 본 학생이 잘 푸는 것처럼, 규칙은 우리가 개발하며 본 질문에는 잘 맞습니다. 그래서 개발 중에 한 번도 보지 않은 새 질문 16개로 다시 시험했더니 규칙은 11개, LLM은 15개를 맞혔습니다. 일상 표현 20개에서 20개를 맞힌 것은 프롬프트를 쓰기 전에 본 문항이라 과대평가이고, 믿을 수 있는 값은 이 한 번도 안 본 질문의 15개입니다."
3. "더 중요한 것은 오른쪽입니다. 질문 이해는 분류에서 끝나지 않고 찾는 범위를 넓힙니다."
4. "첫째, 일상어를 문서에서 쓰는 용어로 바꿉니다. 예를 들어 선생님이 '성홍열도 학교장이 보건소에 신고해야 하나요'라고 물으면, 이 말 그대로는 신고 대상 법정감염병 목록이 후보 60개 중 60위로 나옵니다. 성홍열이라는 병명이 들어가서 병명 없는 목록과 안 맞기 때문입니다. 라우터가 '학교장이 신고해야 하는 법정감염병 종류'로 바꿔서 찾으면 10위, '신고가 필요한 법정감염병 종류'를 넣으면 6위에 들어옵니다."
5. "둘째, 이렇게 바꾼 문장과 원래 질문을 합쳐 두 개로 찾습니다. 같은 데이터에서 상위 10개 안에 정답이 있는 질문이 20개에서 22개로 늘었고, 후보를 30개까지 보면 34개 중 31개입니다."
6. "셋째, 알맞은 Tool로 보냅니다. 학교장이 신고해야 하는지를 묻는 질문은 학교 행동 검색을 주로, 법령을 보조로 쓰게 했더니 근거 없음으로 끝나던 질문이 답을 얻게 됐습니다."
7. "분류 시간은 1.8초 정도입니다."

**질문이 나오면**

- "홀드아웃"이라는 용어는 슬라이드·대본에서 쓰지 않는다. 질문이 나오면: 개발 중 규칙·프롬프트를 고칠 때 보지 않고 따로 빼 둔 시험용 질문이다. 한 번도 안 본 새 질문 16개(원 기록의 홀드아웃 2)에서 규칙 11개, LLM 15개다. 놓친 한 문항은 "수두는 예방접종을 몇 번 맞아야 하나요"를 범위 밖으로 보낸 것으로, 깨끗한 셋을 보존하려고 고치지 않았다. 질문셋과 기대값은 Claude가 작성했고 팀 검수 전이다.
- **라우터 하나가 recall에 준 효과는 분리해 재지 않았다.** 카드 2의 20 → 22는 질문 1개 → 2개를 비교한 값이고, 정답 인용 22 → 25 안에는 두 질문과 문턱 제거가 함께 들어 있다. 카드 1의 60위 → 6~10위는 사례 1건이다. 카드 3의 정답 인용 21 → 22는 실행 간 변동(±2) 안이라 근거 없음 → 답함 사례로만 쓴다.
- 예시의 순위는 hybrid 검색 후보 60개 안에서의 순위다(30위 밖). 병명을 넣은 다른 표현("성홍열은 학교장이 보건소에 신고해야 하는 법정 신고 대상인가요?")도 36위였다. 예시는 1건이라 일반화하지 않는다([라우터 신고 규칙 기록](라우터_신고규칙_S-Q03_20261107.md) 1장).
- 이 쪽의 recall 숫자와 N14의 정답 인용 22 → 31은 대상이 다르다(N14는 최종 출력, 카드 2는 원시 순위).
- temperature 0이어도 같은 질문의 분류가 호출마다 달랐다(S-A04: 8회 중 2회 다름). "절차·방법만 묻는 질문은 학교 행동 하나"를 프롬프트에 넣은 뒤 8회 중 8회 같았다.
- LLM이 실패하면 규칙 분류기로 되돌리고, 실패는 0회였다.
- 방식은 기술 N2(질문 이해), N3(찾기)에서 설명한다.
- 근거: [총정리 5장](발표용_전체과정_검색품질_총정리_20261107.md), [라우터 신고 규칙 기록](라우터_신고규칙_S-Q03_20261107.md), [측정 결과](검색순위_HitMRR_현재구조_20261107.md).

- "판단 실수 예방"의 근거는 N16 ④의 성홍열 신고 사례(전: 의료기관용 24시간 신고를 학교 의무로 씀 → 후: 목록에 없음 + 법 근거)다. 실제 현장 실수가 줄었는지는 모른다.
- 근거: [답변품질_개선과정_정리_20261107-08.md](../20261108/답변품질_개선과정_정리_20261107-08.md), N20, 추출·검증 기록.
