# 학교 정규화·적재·질의 부품 구현 지시서

이 지시서는 `school_learning_reference.ipynb`의 실제 코드·설명을 함께 읽는 것을 전제로 한다. 이전 분석 문서에 나온 함수 이름만으로 작업하지 않는다. 원본 수업 폴더가 없어도 이 노트북 안에서 원본 발췌와 학교 적용 예시를 확인할 수 있다.

## 작업 경계와 완료 목표

팀 개발 지시서 v1.2 §12-1에 따른 school 개인 경로에서 구현한다. 이미 있는 파일과 미커밋 변경을 먼저 확인하고 현재 사용자 작업을 보존한다. 공통 계약·사전·인덱스·환경 변경은 기존 공동 정책에 따라 별도로 처리한다. 코드 또는 노트북이 있다는 이유만으로 실행 결과까지 완료됐다고 가정하지 않는다.

어제 승인된 청크·행동 후보를 입력으로 **정규화 → 실제 공통 Neo4j 적재 → SchoolGraph 단독 검색 → Finding/Citation 반환**을 연결한다. 대표 질문은 ‘유증상 학생 발견 시 담임·보건교사가 확인할 일’이다. 검증된 최소 샘플로 먼저 완주하고 이후 범위를 넓힌다.

코어는 온톨로지 v3.1의 6노드·6관계·27개 의미 속성이다. QueryInput/Output·Finding·Citation은 계약 가이드 v1.2와 실제 공통 모듈을 확인한다. 팀 지시서 §0에 따라 계약은 v1.2 명칭으로 구현한다. 계획서의 이전 DomainResult/Evidence 명칭과 혼합하지 않는다. 승인 상태·구현 차이가 있으면 기록한다.

각 부품은 함수 정의, 작은 입력 예시, 정상/오류 결과, 실제 실행 증빙을 가진다. 참고 노트북의 인공 예시를 공식 지침이나 실제 적재 데이터로 사용하지 않는다.

## B01. 실행 산출물 로더와 승인 후보 연결

- 참고: R00~R01.
- 위치: 정규화 노트북 및 필요시 `src/index/school/normalize.py`.
- 제안 인터페이스: `load_artifacts(run_dir)` → 청크·후보·검수·실행 메타데이터, `select_approved(...)` → ready/held.
- 명시한 완료 실행 폴더를 읽고 후보의 안정적인 키와 chunk_id로 검수 결과를 연결한다. 가장 최근 날짜나 행 번호만 믿지 않는다.
- 필수 문자열, scope/stage/modality, 페이지/원문 검수 상태, 역할 basis와 승인 여부를 확인한다. 원문 raw, 정규화 값, 보류 이유를 구분해 보존한다.
- 수업 shape_ok의 구조 검증과 clean_rows/kept의 보류 패턴을 사용한다. 회사 전용 정리 규칙과 ‘확인 불가도 일부 적재’ 정책은 그대로 적용하지 않는다.
- 검증: 미검수 후보는 held로 이동하며 원본 후보는 소실되지 않는다. JSONL은 NaN/Infinity를 금지한 표준 JSON으로 재읽힌다.

## B02. 청크 소속·원문 근거 검증

- 참고: R02의 find_row, block_all/ends/check 원문과 ref_source_reasons.
- 제안 인터페이스: `validate_source(candidate, chunks, source_parts)` → 오류/보류 이유 목록.
- 문서·청크 소속, PDF 쪽수(1부터), 인쇄 쪽수와 페이지 대조 여부를 확인한다. 표의 역할과 행동이 같은 행/유효한 상위 문맥인지 확인한다.
- 인용은 원문 조각에서 찾는다. 표 제목·머리글·행이 불연속이면 조합된 문장을 원본의 연속 인용으로 취급하지 않는다. 역할표의 예시 단서가 별도 청크이면 해당 근거도 조회/인용 가능하게 연결한다.
- 자동 문자열 검사와 의미·담당·조건의 사람 검수를 구분한다. 편집 메모를 PDF 원문 인용으로 바꾸지 않는다.
- 검증: 다른 문서 청크, 없는 청크, 다른 표 행과 조작된 인용이 승인 집합을 통과하지 않는다.

## B03. 역할·질병·행동 개념 매퍼

- 참고: R03의 rule_link/normalize 및 모호성 검사.
- 제안 인터페이스: `resolve_role(mention, dictionary)` 등 → id/method/status/reason.
- 승인된 정확 표기·별칭의 유일한 매칭만 확정한다. 공백·유니코드 정리는 비교용으로만 적용하고 원문을 보존한다. ‘담임→HOMEROOM_TEACHER’와 같은 연결에는 실제 사전을 쓴다.
- 모호/미등록 값은 사유와 함께 보류한다. NEW_CONCEPT_CANDIDATE는 표준 concept_id가 아니다. 유사도는 후보 추천에만 쓰며 승인 없이 사전·공통 노드를 만들지 않는다.
- 행위 수행자와 수신자를 구분한다. 보건교사에게 전달한 행동의 DONE_BY가 자동으로 보건교사에게도 연결되면 안 된다.
- 검증: 역할 별칭은 같은 ID로 연결되고 서로 다른 수행 역할과 신고/보고/통보 개념은 잘못 합쳐지지 않는다.

## B04. 출처별 ID와 매핑 고정

- 참고: R04. ref_assign_fixture_action_ids는 고정 입력용 데모이며 운영용 증분 ID 생성기가 아니다.
- 실제 `source_manifest.csv`와 common/ids.py가 있으면 재사용한다. 임시 TEMP 값을 공통 DB에 넣지 않는다.
- 문단 `document_id:pNNNN:bNN`, 표 행 `document_id:pNNNN:tNNrNN`, 행동 `document_id:pNNNN:aNN` 형식을 따른다.
- 문서·페이지·원문 위치·행동 분할·역할 등 승인된 기준으로 매핑을 고정하고 재실행에 재사용한다. 승인 후보만 필터한 후 매번 enumerate하면 이후 ID가 밀릴 수 있다. LLM 응답 순서를 ID 기준으로 쓰지 않는다.
- 출처·단계·조건이 다른 SchoolAction은 유지하고 개념만 공유한다. action_id의 식별 번호와 step_order의 절차 순서를 구분한다.
- 검증: 입력 순서를 바꿔도 동일한 승인 레코드의 ID가 유지되고, 두 문서의 같은 개념은 서로 다른 action_id를 가진다. 후보가 추가/보류될 때 기존 매핑이 어떻게 유지되는지도 확인한다.

## B05. 노드·관계 적재 패키지 변환

- 참고: R05의 to_rows/make_props/check_sc40와 ref_build_bundle.
- 제안 인터페이스: `build_load_bundle(...)` → 각 노드·관계의 명시적인 행 목록과 기대 키 집합.
- Document·Chunk·SchoolAction의 속성은 v3.1 허용 목록만 투영한다. 검수 상태, source_chunk_id, 모델명, 프롬프트, 로그·해시는 JSONL에 보존한다.
- HAS_CHUNK, SUPPORTED_BY, DONE_BY(basis 필수), INSTANCE_OF, ABOUT, FOR_DISEASE는 허용된 방향으로만 구성한다. 모든 끝점 존재와 중복 키를 확인한다.
- COMMON/DISEASE_GROUP/UNKNOWN 행동에 특정 질병을 추정해 FOR_DISEASE를 만들지 않는다. ABOUT도 실제 해당 청크/표 행의 질병만 연결한다.
- 필요한 표준 사전 연결이 미완료된 후보의 처리 정책을 명시한다. 우선 정상 경로에는 필수 매핑이 완료된 최소 샘플을 사용한다.
- 검증: 6개 허용 패턴 외 관계, basis 누락, 존재하지 않는 끝점, 사전 밖 ID가 거절된다. 서로 다른 문서의 행동이 하나로 합쳐지지 않는다.

## B06. 배치 적재와 실제 키 검증

- 참고: R06. R08의 기대/실제 키 비교와 함께 사용한다.
- 위치: `src/index/school/load.py` 또는 해당 개인 노트북.
- 제안 함수: upsert_documents/upsert_chunks/upsert_actions/link_evidence/verify_loaded_bundle.
- 기존 승인 제약·인덱스·연결 설정을 확인한다. 공유 사전 노드는 승인된 공통 초기화 방식을 쓰며 개인 적재기는 우선 MATCH하여 연결한다. 자격 증명은 기존 환경 설정으로 받는다.
- 노드는 ID만 MERGE 키, 속성은 허용 목록을 SET한다. DONE_BY는 끝점으로 MERGE한 뒤 basis를 SET한다. 한 번의 실패가 불완전한 행동 경로를 남기지 않도록 작은 트랜잭션 경계를 정한다.
- MATCH 끝점 누락으로 입력 행이 조용히 사라지는 경우를 실제 키 조회로 검출한다. 적재 카운터만으로 완료를 판단하지 않는다.
- 동일 입력을 두 번 넣고 담당 문서 범위의 노드·관계 키 집합이 같은지 확인한다. 팀원이 쓰는 전체 DB 건수는 고정값으로 비교하지 않는다. 조인 집계는 DISTINCT 여부를 검토한다.
- 같은 입력 재실행과 내용 수정 동기화는 다르다. basis/역할/개념 변경 시 오래된 관계가 남을 수 있으므로 삭제·마이그레이션은 기존 소유/승인 정책으로 별도 처리한다. MERGE만으로 동시 적재 관계 중복까지 해결됐다고 주장하지 않는다.

## B07. 해시·실행 장부·실패 재처리

- 참고: R07의 content_hash/run_all.
- 제안 인터페이스: `record_load_result(...)`, `retry_failed_units(...)`.
- 문서/청크/행동 ID, 입력 해시, 승인 데이터·사전 버전, 성공/실패와 확인된 키를 로컬 JSONL에 기록한다.
- 수업의 active/done/schema_version 등을 공통 DB에 새 속성으로 추가하지 않는다. 장부만 보고 skip하지 말고 필요한 DB 존재/근거 경로도 확인한다.
- 실패 단위만 재실행하고, 재시도 횟수를 제한한다. 키나 접속 문자열이 오류 로그에 노출되지 않게 한다.
- 검증: 한 단위 실패 후 다른 단위를 계속 처리하고, 성공 0건과 실행 실패를 구분한다.

## B08. Chunk 우선 검색과 학교 행동 탐색

- 참고: R08의 매개변수 질의와 키 비교. 검색기는 프로젝트 계획에서 도출한 새 부품이다.
- 위치: `src/rag/school/`와 개인 질의 노트북. 다른 slug 내부 모듈은 import하지 않는다.
- 제안 인터페이스: `search_chunks(request)`, `expand_school_actions(chunk_ids, filters)`, `fetch_supporting_chunks(action_ids)`.
- 팀의 승인된 검색 인덱스/기능을 확인하고 질문마다 Chunk 검색을 먼저 실행한다. 역할·행동·비교가 필요하면 SUPPORTED_BY/DONE_BY/INSTANCE_OF를 추가 조회하고 단계 정의·예시 단서도 회수한다.
- 첫 검색과 추가 조회 모두 allowed_document_ids를 적용한다. []는 문서 없음, preferred는 allowed의 부분집합인 순위 힌트다. GYEONGGI 질의에서도 허용된 NATIONAL 지침을 참조할 수 있어야 한다.
- 성홍열 질문을 FOR_DISEASE만으로 처리하지 않는다. 공통 학교 절차와 특정 질병 명시 조치를 구분한다. DISEASE_GROUP는 조건을 그대로 보여 주고 적용을 추정하지 않는다.
- stage는 원문 배치 단계다. 유증상 발견 질문에 대응 제2·3단계 업무를 현재 할 일로 섞지 않는다. 모의 시나리오가 근거라면 예시임을 보존한다.
- 검증: 대표 질문에서 원문/역할을 찾고 허용 문서 밖 결과가 추가 탐색으로 유출되지 않는다. 검색 결과 없음과 DB 오류는 구분한다.

## B09. SchoolGraph와 공통 응답 조립

- 참고: R09~R10은 새로 작성한 설명 예시다. 실제 계약 모듈과 검증기를 우선 import한다.
- 공개 동기 인터페이스는 팀 지시서 §4-2의 `run(query, *, deps=None)`를 따른다. 입력 검증 → 내부 Graph → 출력 검증 순서이며 내부 build_graph 경로의 계약 우회도 확인한다.
- 내부 State에는 request, 검색 조건, chunks, actions, findings, citations, warnings, output 등을 필요에 맞게 둔다. 원래 사용자 질문은 보존하고 task는 세부 작업으로 처리한다. 입력/출력 schema와 실제 반환 필드도 점검한다.
- Finding은 원자적 주장, Citation은 DB 원문·문서·페이지에서 생성한다. 각 Finding에 실제 근거 chunk_ids가 있고, Citation은 chunk_id당 하나다. 같은 청크에 여러 인용이 필요하면 원문을 실제로 지지하는 발췌 범위를 선택한다.
- 최상위 action_ids는 Finding들의 합집합이다. 명시 타입 ID 목록에는 라벨 접두어를 넣지 않는다. context_entity_ids만 혼합 타입 표기를 따른다.
- ANSWERED는 요청을 충분히 충족할 때만, 일부 확인은 PARTIAL, 주장 없음은 INSUFFICIENT_EVIDENCE, 실행 실패는 ERROR로 둔다. 예시 R09처럼 결과가 한 건 있다는 사실만으로 실제 질문을 ANSWERED 처리하지 않는다.
- 검증: 내부 상태 키가 외부 계약으로 새지 않고, 각 상태의 완전한 QueryOutput이 반환된다. 예시 역할을 의무로 표현하거나 원문 충돌을 자동 법적 판정으로 바꾸지 않는다.

## B10. 계약·DB·원문 검증과 증빙

- 참고: R10은 일부 검사 예시다. 공통 validate_query_output와 DB 대조를 대체하지 않는다.
- 구조 검사: 필수 키·타입·상태·허용 문서·Citation 중복·Finding 참조·action 합집합·오류/근거없음의 빈 목록.
- DB 검사: document_id/chunk_id의 존재와 HAS_CHUNK 소속, 페이지 일치, 실제 excerpt, action의 존재와 SUPPORTED_BY, 질병·개념 사전 ID.
- 의미 검사: 주장·조건·기한·담당·modality가 원문과 맞는지 실제 PDF/골든 질문으로 확인한다. 필수 인용과 문자열 포함만으로 의미 검증 완료라고 하지 않는다.
- 개인 최소 검증: T1 대표 질문, T6 가짜 청크/행동 ID 실패, T7 근거 부족, 개인 T8 연결 오류, allowed=[], 역할 예시, 두 문서 동일 개념 유지, 재적재 키 집합 일치.
- 산출물: 정규화/보류 JSONL, 적재 전후 키와 검사 결과, 대표 QueryInput/Output, 실제 Citation 검수표와 오류 사례. 원문·실행 JSONL은 Git 제외 개인 interim에, 노트북·코드·골든 질문은 팀 규칙대로 둔다.

## 노트북 구성과 완료 기준

새 구현 노트북이 필요하면 `notebooks/school/` 안에 영문 소문자·언더스코어 파일명을 사용한다. B01~B07은 정규화/적재 노트북, B08~B10은 단독 질의 노트북으로 나눌 수 있다. 재사용 함수는 개인 src로 옮기고 노트북은 입력·실행·확인 근거를 남긴다. 이전 노트북 커널의 메모리를 자동 공유한다고 가정하지 않는다.

최신 승인 샘플로 실제 공통 DB까지 연결되고, 대표 질문에 실제 Citation을 반환하며, 동일 입력 재적재·근거 부족·오류가 검증되면 오늘 개인 경로가 완주된다. 데이터 규모 확대와 내일 2-Graph 연결은 이 경로가 성립한 뒤 진행한다.
