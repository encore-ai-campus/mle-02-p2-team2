# 그래프 분석과 검색 수업: 오늘 사용할 부품 분석

## 1. 판단과 이전 분석의 보완점

**이 폴더에는 오늘 필요한 검색·질의 부품이 있다.** 정규화·검증·적재에는 기존 `3_LLM_지식추출` 자료가 중심이고, 적재 후 질문에 답하는 SchoolGraph에는 `2_그래프분석과검색`의 38장과 일부 37장 코드가 직접적인 참고가 된다.

이전 참고 패키지는 사용자가 지정한 `3_LLM_지식추출` 범위로 한정했다. 따라서 검색기와 LangGraph 흐름을 ‘프로젝트에 맞춰 새로 설계할 부분’으로 설명한 것은 그 범위에서의 판단이었다. 이번 폴더까지 포함하면 **이미 배운 검색기·출처 formatter·그래프 확장·도구 호출 흐름을 가져와 응용할 수 있다.** 다만 공통 계약과 학교 온톨로지에 맞춘 변환은 여전히 필요하다.

이번에는 폴더의 노트북 16개를 목록·목차·함수/질의 구조로 살피고, 직접 관련된 `38-1~5`, `37-6`, 그리고 GDS·유사도·커뮤니티의 관련 코드를 추가로 확인했다. 아래 셀 번호는 Markdown을 포함해 1부터 세었다. 실제 DB·LLM 호출과 성능 실험은 하지 않았으며, 이 문서는 코드 근거와 프로젝트 적합성 분석이다.

## 3. 부품 S01: Chunk 전문검색

### 실제 수업 코드

`38-1_벡터검색과-전문검색-Vector-FullText인덱스_배포용.ipynb`

- 셀 25: FULLTEXT 인덱스, cjk/standard 계열 analyzer 비교, `count_matches(index, query)`.
- 셀 32: `db.index.fulltext.queryNodes`로 구문/논리 연산 검색.
- 셀 38: `by_text(query, k=3)`와 `by_vector(text, k=3)`.

`by_text()`는 query와 k를 받아 인덱스 검색 → 조문 경로 매칭 → 점수와 상위 결과를 반환한다. 외부 의존성은 Neo4j driver, 인덱스, 수업의 Chunk/PART_OF/Article 데이터, DataFrame 변환이다. 벡터 함수는 추가로 embedder에 의존한다.

### 프로젝트 적용

팀 지시서는 fulltext로 시작하고 벡터는 검증 후 추가하는 기본값을 제시한다. 따라서 오늘 가장 먼저 응용할 검색 함수는 `by_text()`다. 수업의 `PART_OF→Article`을 `Chunk←HAS_CHUNK−Document`로 바꾸고 실제 chunk_id와 문서/페이지를 반환한다.

아래는 구조 설명용 학교 질의다. 실제 인덱스 이름·구성·버전·검색 입력 규칙은 공통 DB에서 확인한다.

```cypher
CALL db.index.fulltext.queryNodes($index_name, $search_expression)
YIELD node AS c, score
MATCH (d:Document)-[:HAS_CHUNK]->(c:Chunk)
WHERE d.document_id IN $allowed_document_ids
RETURN d.document_id AS document_id, c.chunk_id AS chunk_id,
       c.text AS text, c.section AS section,
       c.pdf_page AS pdf_page, c.printed_page AS printed_page, score
ORDER BY score DESC, chunk_id
LIMIT $k
```

제안 인터페이스는 `search_school_chunks(request, search_terms, k)` → 출처를 가진 hit 목록이다. LLM이 원문 질문 전체를 바꾸도록 맡기기보다 질문을 보존하고 승인 별칭·역할명·행동 개념으로 검색어를 구성하는 부분을 별도로 둔다.

주의할 점:

- 자연어 질문 전체를 fulltext 질의로 넘겼다고 원하는 의미 검색이 자동으로 되는 것은 아니다. ‘담임/담임교사’, ‘보건/보건교사’, ‘유증상/증상 발견’ 등 실제 표현 차이를 시험한다.
- Cypher 파라미터 사용과 fulltext 검색식의 문법 처리는 다르다. 사용자 문자열의 특수기호를 무조건 Lucene 연산자로 실행하지 않도록 검색식 생성/이스케이프 정책을 둔다.
- 검색 결과를 LLM에 전달하기 전에 허용 문서 필터를 적용한다. preferred는 순위 힌트이며 allowed를 대신하지 않는다.
- 인덱스 생성 셀을 그대로 실행하지 않는다. 같은 이름의 인덱스가 이미 있으면 `IF NOT EXISTS`가 analyzer나 차원을 원하는 값으로 바꿔 주는 것은 아니다. 승인된 실제 설정과 ONLINE 상태를 확인한다.
- 검색 점수는 관련성 점수다. 사실의 정확성, 최신성, 적용 가능성 점수로 표현하지 않는다.

## 4. 부품 S02: 출처를 보존하는 검색 결과 formatter

### 실제 수업 코드

`38-2_리트리버-Vector와-Hybrid검색_배포용.ipynb` 셀 27의 `with_source(record)`는 record의 node와 score를 읽고 `RetrieverResultItem(content=..., metadata=...)`을 반환한다. 내용에 근거 ID를 붙이고 metadata에 조문·청크·점수를 보존한다.

셀 20~21의 `top_articles()`와 비교표는 기대 조문이 상위 결과에 있는지 확인한다. 셀 33~34는 RagTemplate/GraphRAG와 `return_context=True`로 답변과 검색 근거를 함께 확인한다.

### 프로젝트 적용

우리에게 중요한 것은 VectorRetriever라는 클래스 자체보다 **원문과 식별자를 검색 단계부터 구조적으로 들고 다니는 패턴**이다.

학교용 hit에는 document_id, chunk_id, pdf_page, printed_page, section, text, score를 유지한다. 문서 제목·판본이 필요하면 Document에서 함께 가져온다. 최종 Citation은 이 데이터와 실제 DB 대조 결과로 만든다.

수업의 `node['id'].split('#')[0]`은 법령 조문 ID 규칙이다. 프로젝트 chunk_id에 적용하지 않는다. 문서 ID는 `HAS_CHUNK`로 확인한다. `short_source()`처럼 text를 80/300자로 자르는 방식은 미리보기에만 쓰고, 조건·단서가 잘린 본문으로 최종 답을 생성하지 않는다.

가능하면 content 문자열을 `ast.literal_eval`로 다시 해석하는 수업 보조 패턴보다 metadata와 구조화된 레코드를 직접 사용한다. 이렇게 해야 LLM 출력이나 문자열 모양에 출처 연결이 좌우되지 않는다.

## 5. 부품 S03: Vector/Hybrid 검색은 조건이 갖춰졌을 때

### 실제 수업 코드

- 38-1 셀 8·13·20: 1536차원 벡터 인덱스, query embedding, 인덱스 검색 후 그래프 조건 필터.
- 38-2 셀 9: `VectorRetriever`.
- 38-2 셀 15: `HybridRetriever`.

Hybrid는 이 수업 코드에서 벡터 인덱스·전문검색 인덱스·embedder를 모두 받는다. fulltext만 준비된 상태에서 같은 클래스를 즉시 사용할 수 있다고 가정하지 않는다.

### 사용 조건과 검증

Chunk.embedding이 실제 준비돼 있고, 질문 임베딩과 저장 임베딩의 모델·차원·전처리가 일치하며, 승인된 인덱스가 준비된 경우 선택한다. 수업의 1536이라는 숫자를 현재 모델에도 맞는 고정값으로 쓰지 않는다.

벡터 상위 후보를 먼저 k개 뽑은 뒤 허용 문서 필터를 걸면, 관련 허용 청크가 전체 후보 밖에 있어 결과가 비는 문제가 생길 수 있다. 사용 라이브러리/버전의 사전 필터 지원을 확인하거나, 승인된 후보 확대·재시도 한도와 문서 범위 검색 전략을 둔다. 응답 단계의 후처리만으로 허용 밖 정보의 LLM 유입을 막을 수는 없다.

오늘은 fulltext 기준선을 확보한 뒤 같은 소규모 질문에서 벡터/Hybrid의 근거 회수 개선이 확인될 때 도입한다. ‘Hybrid니까 더 좋다’는 가정으로 먼저 구조를 복잡하게 만들지 않는다.

## 6. 부품 S04: 검색한 청크에서 행동·역할·개념으로 확장

### 실제 수업 코드

`38-3_그래프로-근거넓히기-VectorCypher와-PageRank재랭킹_배포용.ipynb`

- 셀 10의 `EXPAND`: 검색 결과의 node/score에서 Article과 위임 경로를 찾아 추가 속성 반환.
- 셀 11의 `expanded_item(record)`: 확장 결과를 content와 metadata로 변환.
- 셀 17~18: 일반 검색과 `HybridCypherRetriever`의 답변 비교.
- 셀 40의 `answer_with(items, question)`: 선정한 근거로 context를 구성하고 답변.

### 프로젝트 적용

오늘 GraphRAG에서 가장 직접적인 부품이다. 라이브러리의 VectorCypher/HybridCypher 클래스를 꼭 사용하지 않아도 **검색 → 고정 Cypher 확장 → 근거 레코드 반환**이라는 동일 원리를 적용할 수 있다.

학교 프로젝트 경로는 다음과 같다.

```text
검색 Chunk ← SUPPORTED_BY − SchoolAction
SchoolAction − DONE_BY(basis) → SchoolRole
SchoolAction − INSTANCE_OF → ActionConcept
ActionConcept ← INSTANCE_OF − 다른 출처 SchoolAction
각 SchoolAction − SUPPORTED_BY → Chunk ← HAS_CHUNK − Document
```

첫 확장에서는 검색된 청크에 연결된 행동과 역할·개념·조건을 찾는다. 문서 비교 질문일 때만 같은 ActionConcept의 다른 출처 행동까지 확장한다. 각 행동은 원문별로 유지한다.

단계 정의·예시 역할 단서·추가 조건이 다른 청크에 있다면 실제 근거 경로와 그 텍스트도 가져온다. **관련 노드의 ID 목록만 반환한 것과 실제 근거 본문을 회수한 것은 다르다.** 수업의 경로 ID 표시를 그대로 쓰면 우리의 Citation 요구를 충족하지 못할 수 있다.

확장 제약도 필요하다.

- 모든 문서·추가 청크에 allowed 필터를 반복 적용한다.
- 같은 개념은 ‘비교 후보’이지 양쪽 조치의 상호 증명이 아니다.
- role이나 disease를 경유해 연결된 모든 행동을 무제한 확장하지 않는다. 범용 역할 노드는 너무 많은 결과를 가져올 수 있다.
- hop 수보다 관계 종류·문서 수·행동 수·근거 텍스트 예산을 먼저 제한한다.
- 여러 역할/근거/개념을 OPTIONAL MATCH로 한꺼번에 붙이면 행이 곱해질 수 있다. 실제 ID별 수집과 관계별 분리 집계를 사용한다. 역할과 basis를 서로 다른 리스트로 모아 짝을 잃지 않는다.
- stage/scope/when_text/modality와 EXAMPLE를 끝까지 유지하고 현재 상황에 적용된다고 자동 단정하지 않는다.

### 실제 수업 코드

### 프로젝트 적용

학교 행동 조회가 필요한 오늘에는 자유 Text2Cypher보다 다음처럼 용도가 명확한 함수가 적합하다.

| 제안 도구/함수 | 목적 | 필수 반환 정보 |
|---|---|---|
| search_school_chunks | 원문 청크 먼저 회수 | 청크·문서·쪽수·원문 |
| get_role_actions | 특정 단계·담당의 행동 | action_id, 역할/basis, 조건, 근거 |
| compare_action_sources | 같은 개념의 출처별 비교 | 문서별 행동과 각 근거 |
| get_action_evidence | 특정 행동의 실제 근거 확인 | SUPPORTED_BY/HAS_CHUNK 경로 |

수업은 도구 결과를 문자열로 반환하지만, 우리 내부 함수는 구조화 레코드를 보존하는 편이 유리하다. 모델에 보여 줄 텍스트와 Citation 생성용 원본 데이터를 별도로 관리한다. 도구의 설명은 언제 사용하고 무엇을 알 수 없는지를 명시한다.

allowed_document_ids는 신뢰할 수 있는 요청 State/deps에서 주입한다. LLM의 도구 인자로 허용 범위를 자유롭게 바꾸게 하지 않는다. 검색을 먼저 해야 한다는 프로젝트 정책도 프롬프트에만 두지 말고 실행 흐름으로 보장한다.

## 8. 부품 S06: LangGraph 실행 흐름과 로그

### 실제 수업 코드

`38-5_세-방법-비교와-라우터-벡터RAG-GraphRAG-Text2Cypher_배포용.ipynb`

- 셀 45 `search_text`, `search_with_graph`, `query_graph`: 리트리버를 도구로 감싸기.
- 셀 50 `agent`, bind_tools, StateGraph(MessagesState), ToolNode(handle_tool_errors=True).
- 셀 51 `ask_agent`: recursion_limit, 실제 tool_calls 목록 기록.

따라서 SchoolGraph의 도구 호출 부분에는 이 폴더의 직접적인 학습 근거가 있다. 현재 참고 패키지가 다루지 않았던 부분이다.

### 프로젝트 적용

오늘은 기본 흐름을 ‘입력 검사 → 청크 검색 → 필요한 고정 그래프 조회 → 주장/근거 구성 → 계약/DB 검증’으로 구성하고, 자유 도구 반복은 실제 필요할 때 붙이는 것을 권한다.

수업의 MessagesState와 최종 message.content를 그대로 QueryOutput으로 반환하지 않는다. 공개 run(query, deps)에서 QueryInput을 받고, 내부 메시지와 구조화 조회 결과를 연결한 뒤 Finding/Citation을 조립하는 어댑터가 필요하다. 내부 State·프롬프트·도구는 자유지만 외부 계약은 팀 기준을 지킨다.

ToolNode의 handle_tool_errors=True는 오류를 메시지로 넘기는 장치다. **오류가 근거로 바뀐 것은 아니다.** 도구 오류를 자연어 주장으로 사용하지 말고 ERROR/PARTIAL/재시도 분기에 반영한다. 루프 횟수, 검색 횟수와 텍스트 예산을 제한하고 실제 호출 도구·청크 ID·실패를 기록한다. 원문이 없는 답은 모델 상식으로 보충하지 않는다.

## 9. 부품 S07: 검색 방식 라우터와 평가

38-5 셀 34의 `route(question)`는 COUNT_WORDS가 있으면 Text2Cypher, 아니면 GraphRAG로 보낸다. 셀 62의 `route_graph()`는 먼저 데이터 도메인을 고르고 그 뒤 검색 방식을 고른다.

이 아이디어를 우리 프로젝트에서는 두 단계로 구분한다.

1. Orchestrator가 School/Respiratory/PreventionLegal 중 필요한 전문 Graph를 선택한다.
2. 각 Graph 내부에서 원문 검색만으로 충분한지, 행동·역할·문서 비교 탐색이 필요한지 선택한다.

오늘 개인 SchoolGraph 내부 라우팅과 내일 공동 Orchestrator의 도메인 선택을 같은 함수로 섞지 않는다. ‘몇 일’은 등교중지 기간 원문 질문일 수 있어 count 질의로 보낼 수 없다. 표면 낱말만으로 숫자 질문을 분류하는 수업 규칙은 단순 기준선이며 실제 질문으로 개선해야 한다.

평가 부품은 즉시 참고할 가치가 있다.

- 38-2의 top_articles/비교표 → 기대 근거 청크가 top-k에 들어오는지 확인.
- 38-3의 일반/확장 답변 비교 → 그래프 추가 조회가 담당·조건·다른 출처 근거 회수에 도움되는지 확인.
- 37-6·37-7의 도구 선택 표 → 기대 도구와 실제 호출 비교.
- 38-4의 run_all → 생성 Cypher·결과·실행 오류를 질문별로 격리 기록.
- 38-5의 is_correct/ask → 방법별 결과 비교의 기본 구조.

정답 낱말이 모두 있다는 검사만으로 ‘정답’으로 승인하지 않는다. 부정문 처리, 원문 담당, 조건·기산점, 단계, 예시/의무, 출처 연결을 추가로 본다. 수업의 점수는 보고서 구조의 참고이며 우리 프로젝트 정확도 수치로 재사용하지 않는다.

## 10. 부품 S08: Text2Cypher는 어떤 조건에서 쓸까

38-4 셀 21은 SCHEMA·값 규칙·EXAMPLES·t2c_item과 Text2CypherRetriever를 보여 준다. 셀 11의 run_all은 실제 생성 질의와 결과/실패를 기록한다.

일반적인 새로운 집계 질문을 많이 받아야 한다면 후속 후보가 될 수 있다. 하지만 오늘 대표 질문은 검증된 역할·행동·근거 조회이며, 고정 Cypher로 충분히 표현 가능하다. 자유 생성 질의를 먼저 도입할 필요는 낮다.

도입한다면 학교 6노드·6관계와 ID/허용값, 문서 접근 범위·중복 집계 규칙을 제공하고 실제 읽기 권한·질의 시간/결과 제한을 검증해야 한다. 읽기 routing은 쓰기 권한 차단 그 자체가 아니다. 수업도 READ routing을 통한 쓰기 시도 셀에 ‘보장은 아님’이라고 적었다. 문자열 금지어 필터만으로 읽기 전용을 보장했다고 판단하지 않는다.

집계가 맞아도 행위 근거를 반환했다는 뜻은 아니다. generated Cypher와 COUNT 숫자는 Citation을 대신하지 않는다. 학교 사실 답변에는 해당 원문·문서·쪽수로 내려가는 경로가 여전히 필요하다. 잠복기·격리 기간을 Disease의 새 속성으로 만들어 답하는 방식으로 스키마를 바꾸지 않는다.

## 11. GDS·유사도·커뮤니티를 후순위로 두는 이유

### PageRank/PPR/Betweenness

연결이 많은 역할·행동은 문서에 많이 등장했기 때문에 중심성이 높을 수 있다. 이것이 최신 지침, 법적 효력, 현재 학생에게 적용되는 조치라는 뜻은 아니다. 38-3의 rerank는 검색 점수와 PageRank를 가중 합한다. fulltext 점수와 벡터/Hybrid 점수의 범위를 같다고 가정하거나 수업 weight=0.3을 그대로 쓰면 의미가 달라질 수 있다.

PPR은 별도 실험에서 후보 발견에 활용할 수 있지만 방향·허용 문서·노드 타입·평가 질문을 명시해야 한다. 36-4의 pagerank 속성 write는 승인 스키마 밖 속성 변경이 될 수 있다.

### NodeSimilarity/KNN

37-2는 공통 이웃과 임베딩 유사도를 구분한다. 학교에서는 같은 역할이나 청크에 연결됐다는 이유로 행동 의미가 같지 않다. KNN 후보도 동일 행동·규칙이라고 자동 확정할 수 없다. 수업이 생성하는 SIMILAR_BY_CASES 같은 관계를 새 코어 관계로 추가하지 않는다.

### 커뮤니티와 요약

37-4는 Community, 37-7은 CompanyGroup 같은 요약 노드를 만든다. 현재 6노드 코어에는 이런 노드가 없다. 필요하면 별도 승인·실험을 거친다. 38-3의 same_community는 상위 결과와 같은 무리만 남기므로 다른 문서의 예외/충돌 근거를 제거할 수 있다. 출처별 비교를 목표로 하는 우리 프로젝트에서 기본 필터로 삼기 어렵다.

### 최단 경로

‘유증상 발견 → 보호자 연락 → 보고’라는 업무 순서는 가중 최단 경로가 아니다. 현재 그래프에는 절차 NEXT 관계와 이동 비용이 없고 step_order는 원문의 순서다. 그래프에서 짧은 연결을 찾았다는 이유로 단계나 해야 할 조치를 새로 추론하지 않는다.

### 시각화

37-4의 NetworkX 방향 그래프 시각화는 실제 DB 조회 결과로 그래프 증빙을 만들 때 참고 가능하다. 노드 색을 6종 라벨로, 간선을 관계명으로 구분하고 Document→Chunk와 Action→Chunk 경로가 보이게 할 수 있다. 예시로 그린 그림과 실제 DB 데이터를 시각화한 증빙을 구분한다. 이는 질의 완주 후의 보조 작업이다.

## 13. 오늘에 대한 최종 권장안

정규화·적재는 기존 3_LLM 참고 패키지를 사용한다. 검색·SchoolGraph는 이 폴더에서 **fulltext 검색, 출처 formatter, 고정 관계 경로 확장, 도구/State 흐름과 평가**를 가져온다. 베이스라인은 fulltext + 매개변수 Cypher이며, 벡터/Hybrid는 실제 준비 상태와 비교 결과를 보고 선택한다.

이 조합은 계획서의 ‘Chunk 검색 우선 → 필요한 그래프 탐색 → 원문 검증’과 온톨로지의 ‘출처별 행동 유지 → 공통 개념 연결’, 계약의 ‘Finding/Citation 반환’을 함께 만족하도록 설계할 수 있다. 각 부품은 모델 출력이 아니라 실제 DB와 원문을 통해 검증해야 한다.
