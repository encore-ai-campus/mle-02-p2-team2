# 11/04 코드에서 v2.0 Tool 구조로 이행할 지점

2026-11-05에 실제 로컬 코드를 읽어 작성했다. 코드와 노트북을 실행하거나 실DB를 조회하지 않았으므로 완료 실적/DB 적용 여부를 새로 판정하지 않는다. 사용자가 완료했다고 알려 준 11/02~04 자산은 보존·재사용한다. 검토 파일 해시는 `reference_manifest_20261105.json`에 남긴다.

## 2. 실제 코드에 필요한 변경

### M01. v1.2와 v2.0의 입력/출력 경계 분리

`contract_local.validate_query_input()`은 허용 키를 엄격히 제한해 v2.0의 선택 `request_id`가 들어오면 거절한다. 기존 SchoolGraph 어댑터를 이용할 때는 그대로 전체 v2 요청을 넘기지 않는다. 메인 QueryInput을 먼저 v2로 검증하고, 레거시 호출에 필요한 필드만 명시적으로 투영한다.

기존 QueryOutput은 domain/status/findings/citations/action_ids/warnings/answer다. ToolResult는 tool_name/status/findings/citations/graph_paths/warnings로 바뀐다. **domain→tool_name만 바꾸면 끝나는 이행이 아니다.** answer는 메인이 만들고, action_ids는 최종 메인 응답에서 Finding의 합집합으로 계산한다. 기존 전문 출력 validator에 v2 결과를 넣지 않는다.

레거시 상태는 ANSWERED→OK, PARTIAL→PARTIAL, INSUFFICIENT_EVIDENCE→NO_EVIDENCE, ERROR→ERROR로 변환할 수 있다. 단, 원래 guard에서 범위 밖으로 종료한 경우의 INSUFFICIENT_EVIDENCE는 단순 검색 실패와 구분해 메인 범위 분기로 올려 처리한다. 결과가 검증됐다는 전제 없이 상태만 바꿔 통과시키지 않는다.

### M02. 고정 ‘청크 우선’ 경로를 모든 Tool의 전제로 두지 않기

기존 graph.py는 guard→search→expand→verify 순서이고 search.py에 이미 있는 `get_role_actions()`를 직접 주 경로로 쓰지 않는다. v2.0 Action Tool은 역할/행동/개념으로 직접 Cypher 탐색 후 원문을 회수할 수 있다. fulltext·vector·hybrid는 필요한 Tool 내부 선택이다.

초기에는 기존 compiled Graph를 감싸도 된다. 이후 Action 직접 관계 조회 경로를 분리하면 불필요한 청크 검색·임베딩 의존성을 줄일 수 있다. 기존 검색의 회귀 사례는 유지한다.

### M03. 임베딩·DB 의존성을 필요할 때 준비

기존 `default_deps()`는 OPENAI_API_KEY가 있으면 embedder를 만든다. key 존재 자체를 모든 Tool의 임베딩 필요성으로 해석하지 않는다. Action의 고정 Cypher 경로에는 driver/database/사전만 주입할 수 있어야 한다. 같은 질문을 네 Tool 모두 동일한 모델로 임베딩할 의무는 없다.

Tool 하나가 호출 후 공유 driver를 닫지 않도록 자원 소유권을 확인한다. 메인이 생성한 공통 의존성의 종료는 메인/서비스 경계에서 관리한다.

### M04. GraphPath 수집과 검증 추가

현재 `get_role_actions()`는 action_id/document_id/chunk_id와 역할·basis 목록을, `get_action_evidence()`는 SUPPORTED_BY/HAS_CHUNK에 대응하는 원문 레코드를 반환한다. 이 확인된 끝점·관계에서 GraphEdge를 만든다. 누락된 관계를 질문이나 LLM 설명으로 채우지 않는다.

기존 `verify_against_db()`는 Citation 소속·쪽수·인용과 Action 근거, 사전 ID를 확인하지만 GraphPath는 검사하지 않는다. 실제 방향·관계 종류·양 끝 ID, 경로와 허용 문서 범위를 별도로 검사한다. `source_ref`를 ':' 전체 split으로 해체하면 action_id 안의 ':'가 깨지므로 첫 ':'만 타입 구분자로 다룬다.

### M05. 스키마 v3.1 전제를 실제 적용 상태와 분리

현재 ACTION_FIELDS는 a.stage/a.step_order/r.basis를 읽고, 단계 필터와 정렬에서 이 필드를 사용한다. 코드에 있다는 사실은 DB 전체가 v3.1이라는 증거가 아니다. 필드가 없으면 null이 반환되거나 필터에 의해 결과가 빠질 수 있다.

시작 시 승인 기록과 실제 문서 범위의 데이터·속성·관계·인덱스를 확인한다. v3.1 미적용 상태를 임의 값으로 채우지 않고 stage/step_order/basis의 제공 가능성 및 응답 한계를 기록한다. basis가 미확인인 관계를 EXPLICIT로 만들지 않는다. 필요하면 해당 질의를 호환 경로로 분기하고 적용 조건이 불명확한 부분을 경고/보류한다.

### M06. 메인 범위·의도 판별을 전문 검색 guard와 구분

기존 `plan_question()`은 학교 내부 역할·단계·비교·법정 신고 힌트에 특화돼 있다. 이를 서비스 전체 분류기로 그대로 쓰지 않는다. 병명 없는 학교 업무는 Action, 질병 사실은 Disease, 신고/법령은 Legal, 문서별 비교는 CrossDoc이라는 메인 분류를 추가한다.

기존 모의훈련 근거만 있을 때 PARTIAL 처리, 법적 신고 의무를 학교 자료만으로 확정하지 않는 처리, 역할 일부 누락 경고는 유지할 가치가 있다. 새 구조에서는 legal_duty 등에서 드러난 미해결 작업을 메인에 전달할 수 있게 한다. Tool이 주 작업을 마쳤어도 원질문이 복합적이면 전체 ANSWERED로 단정하지 않는다.

### M07. 비교 조회 책임은 점진적으로 분리

기존 `compare_action_sources()`는 같은 개념의 다른 출처를 이미 조회한다. 이를 폐기하지 말고 CrossDoc 담당자에게 입력/결과/허용 범위/원문 경로를 전달할 수 있는 재사용 자산으로 정리한다. 오늘 주승우가 별도 완성 CrossDoc Tool을 중복 구현하지 않는다.

### M08. 최종 응답·상태·호출 기록과 검증

메인 QueryOutput에서 domain은 사라지고 response_type/tools_used/search_rounds가 필요하다. response_type DOMAIN/GENERAL/OUT_OF_SCOPE별 근거 요구와 최종 상태를 적용한다. NO_EVIDENCE와 ERROR를 분리하고, ToolResult의 OK를 원질문 전체 완료로 자동 해석하지 않는다.

tools_used에는 실제 호출 순서, search_rounds에는 실제 Tool 호출 횟수를 기록한다. 내부 DB 보조검색이나 LangGraph 노드 수를 Tool 횟수로 세지 않는다. 실패한 실행 시도도 호출한 사실로 기록하고, 등록조차 안 된 Tool을 선택한 경우에는 호출 없이 연결 오류로 남긴다.

최종 QueryOutput에는 graph_paths 필드가 정의돼 있지 않다. 경로는 ToolResult/내부 실행 기록·시각화 증빙에 보존하고 외부 계약에 임의로 추가하지 않는다. Citation 중복을 제거할 때 같은 청크의 다른 발췌를 무조건 첫 항목으로 버리지 말고 실제로 주장을 지지할 범위를 확인한다.

## 3. 유지할 검사와 오늘 새로 추가할 검사

기존의 실제 ID/페이지/인용, allowed=[], 허용 문서 밖 차단, 모의 시나리오/예시 역할, DB 실패 분리는 유지한다. 오늘은 v2 입력·출력 타입, expected tool_name 일치, GraphPath 실재성, request_id 수용, 일반/범위 밖 분기 0회 호출, 단일 Tool 호출 이력, Tool 실패와 NO_EVIDENCE 구분을 추가한다.

11/06의 CrossDoc·재검색 루프 검증은 준비 항목으로 분리한다. 오늘 완료 기준은 Action 단독 ToolResult와 메인 한 Tool 실제 호출→공통 Neo4j→Finding/Citation→QueryOutput이다. 팀 전체로는 Disease/Legal도 각각 단독 호출 결과가 있어야 한다.
