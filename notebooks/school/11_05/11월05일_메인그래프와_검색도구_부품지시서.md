# 11/05 부품 지시서: ActionSearchTool + 메인 LangGraph 첫 연결

## 0. 오늘의 기준과 범위

함께 제공한 `reference_project_plan_v2_20261105.md`, `reference_tool_contract_v2_20261105.md`, `reference_schedule_v2_20261105.md`를 기준으로 한다. 원본 팀 문서가 갱신됐다면 최신 확정본과 차이를 먼저 확인한다. 각 부품은 `school_tools_reference_20261105.ipynb`의 D번호를 참조한다. 수업 함수 본문·의존성은 노트북 안에 있으므로 원본 수업 경로가 없어도 작업할 수 있다.

**오늘 주승우 완료 목표:** 기존 학교 검색 자산을 Action Tool로 래핑하고, 메인 LangGraph에서 사용자 질문 하나→선택 Tool 하나→공통 Neo4j→실제 Finding/Citation→v2.0 QueryOutput을 실행한다. 팀 전체로는 Action/Disease/Legal 각각의 단독 ToolResult가 필요하다.

CrossDoc 완성·본격 근거 평가/다음 Tool 재진입·총 3회 호출 제한 루프는 11/06의 주 목표다. 오늘은 올바른 1회 종료 경로와 확장 가능한 경계를 만든다. 충분하지 않은 결과를 ANSWERED로 과장하거나 fake Tool을 실제 팀 Tool 완료로 보고하지 않는다.

## 1. 구현 전 확인과 기존 작업 보호

현재 코드의 구체적인 재사용/변경 지점은 **`11월04일코드_v2_이행점검.md`**를 먼저 읽는다. 현재 확인한 버전에서 다음 부품이 이미 있다.

- search.py: 청크 검색, 역할 직접 조회 `get_role_actions`, 행동 근거 `get_action_evidence`, 동일 개념 비교 `compare_action_sources`.
- graph.py: 기존 SchoolGraph 계획·검색·주장/근거 조립·DB 검증·실행 추적.
- validation_local.py: 기존 Citation/Action/사전 ID DB 대조.
- contract_local.py: v1.2의 입력/출력 검사. v2.0 결과를 검사할 수 있는 파일로 간주하지 않는다.

먼저 Git 상태와 적용 AGENTS.md를 확인한다. 수정 중인 코드·노트북·테스트를 보존한다. 이번에는 11/04 적재·정규화 전체를 다시 구현하지 않는다.

실제 구현 파일은 주로 `src/rag/school/`의 개인 범위에 두고, 실험은 `notebooks/school/`에 둔다. 메인 코드를 최종적으로 공동 `rag/orchestrator` 또는 새 공통 경로로 옮기려면 팀의 현재 파일 배치·동시 작업을 확인한다. **v2.0은 아키텍처 변경이지 새 공용 폴더를 임의로 만들라는 지시가 아니다.** 초기 메인 실험은 개인 노트북/모듈에서 검증해 전달 가능하게 한다. 공동 타입·검증기는 유종혁 중심으로 연동하고, 개인 사본을 별도 확정 계약으로 만들지 않는다.

## B01. DB 기능·스키마·기존 검색 인터페이스 확인 부품

**참고:** D01/D05, 이행 점검 M02/M03/M05.

**제안 인터페이스:** `inspect_search_capabilities(driver, database, document_ids)` → 확인 시점·DB 대상·스키마 기능·데이터 범위·사용 가능한 검색 경로 보고서.

읽기만 수행해 연결 대상, 문서 ID, 주요 노드/관계, 근거 경로, 실제 인덱스와 승인 기록을 확인한다. 문서에 v3.1이 있다는 사실로 실DB 적용을 가정하지 않는다. stage/step_order/DISEASE_GROUP/basis/embedding의 존재·검수·사용 가능성을 담당 문서 범위에서 확인한다.

코드에서 확인된 데이터 필드가 비어 있으면 원문 근거 없는 값을 채우지 않는다. v3.0 호환 경로와 v3.1 지원 경로를 선택하는 정책을 명시한다. 속성 하나가 없다는 이유로 문서 전체를 근거 없음으로 처리하지 않되, 담당/단계 주장에 필요한 근거가 없으면 해당 주장은 보류·PARTIAL 처리한다.

기존 driver/database/사전을 deps로 재사용한다. Action 직접 질의에 임베딩은 필수가 아니다. 공유 driver 수명과 Tool별 종료 책임을 확인한다. DB DDL/데이터 쓰기·재적재는 이 부품의 일부가 아니다.

**검증/증빙:** 실제 접속 대상(비밀값 제외), 문서·관계 샘플, 스키마 승인/적용 차이, 선택한 검색 방식과 제한을 로컬 실행 기록에 남긴다. 운영 DB를 확인하지 않았다면 완료로 표시하지 않는다.

## B02. v2.0 계약·입력/출력 어댑터

**참고:** D06 계약 원문, D07 레거시→Tool 변환, 이행 점검 M01/M08.

**입출력 경계:** 서비스는 QueryInput→QueryOutput, Tool은 ToolInput→ToolResult다. v1.2 domain/answer 중심의 전문 Graph 봉투는 Tool 경계에서 변환한다.

공통 타입/validator가 이미 있으면 import한다. 아직 없다면 팀원과 합의한 로컬 임시 모듈을 개인 범위에 두고, 계약 사본 §9의 정의를 그대로 사용해 추후 import만 교체할 수 있게 한다. 임의 필드명 변경은 하지 않는다.

- QueryInput의 원래 question은 유지하고 request_id는 실행 상관관계 ID로 처리한다.
- ToolInput의 task는 필수다. preferred/context/top_k는 선택이다.
- allowed는 신뢰하는 서비스 정책에서 넣고 모든 검색·경로 조회에서 강제한다. []는 허용 문서 없음이다.
- preferred는 allowed의 부분집합인 순위 힌트다. Tool을 자기 담당 PDF에 고정하지 않는다.
- ToolResult에는 tool_name/status/findings/citations/graph_paths/warnings만 공통 필드로 둔다. 실제 호출 Tool 이름과 반환 tool_name도 비교한다.
- Tool 상태 OK/PARTIAL/NO_EVIDENCE/ERROR를 최종 응답 상태와 구분한다.

레거시 Graph를 감쌀 때는 request_id 등을 v1.2 validator에 그대로 넘기지 않도록 허용 필드만 투영한다. 기존 run의 원문/DB 검사와 PARTIAL 경고를 보존한다. 새 QueryOutput은 response_type와 tools_used/search_rounds를 포함하고 domain은 쓰지 않는다.

**검증:** 필수 키·중첩 타입·정수/불리언 페이지 구분·잘못된 preferred·잘못된 Tool 이름·빈 근거·request_id 포함 요청을 검사한다. TypedDict만 선언해 실행 검증이 끝났다고 하지 않는다.

## B03. 작업 단위 계획·검색 조건 구성

**참고:** D02 전문검색/formatter, D04 라우터. 기존 `plan_question`, `build_search_terms`, 사전 연결을 재사용한다.

**제안 인터페이스:** `plan_action_task(tool_input, dictionaries, capabilities)` → 명시적 역할/개념/단계 후보, 검색어, 적용 범위와 미해결 항목.

역할명·질병명·개념 ID는 승인 사전으로 해석한다. context_entity_ids는 첫 ':'를 기준으로 타입/실제 ID를 나눈다. ID 존재와 허용 범위도 검증한다. ‘보건소’의 보건을 보건교사로, ‘보건교사에게 전달’의 수신자를 수행자로 혼동하지 않는다.

명시 단계·질문 상황은 원문 검색 힌트로 쓰되, 현재 학생의 대응 단계를 자동 확정하지 않는다. 조건·단계가 다르면 분리해 표시한다. COMMON을 모든 특정 질병에 상속하거나 DISEASE_GROUP를 질병 목록으로 추정 확장하지 않는다.

검색 계획은 질문을 바꾸지 않고 별도 자료구조로 둔다. fulltext/vector/hybrid는 해당 Tool이 선택한다. 벡터가 준비되지 않았으면 fulltext·고정 Cypher 경로로 시작하고, 다른 Tool에 같은 embedder를 강제하지 않는다.

**검증:** 병명 없는 담임/보건교사 질문을 계획할 수 있고, 역할 수신자·별칭 오인과 원문 미확인 단계의 확정을 피한다. 조건이 불명확하면 그 사유가 다음 단계로 전달된다.

## B04. 실제 행동·역할·근거 조회와 구조화 결과

**참고:** D03 고정 질의·그래프 확장, D07의 인공 Action Tool. 실제 재사용: `get_role_actions`, `expand_school_actions`, `get_action_evidence`.

**제안 인터페이스:** `retrieve_action_records(tool_input, plan, deps)` → 행동별 레코드·근거 청크·조회한 관계 끝점·미해결 항목.

역할/단계/개념이 분명하면 검증된 매개변수 Cypher로 직접 SchoolAction과 DONE_BY/SUPPORTED_BY/HAS_CHUNK를 탐색할 수 있다. 청크 검색이 필요한 표현이면 기존 검색 뒤 연결된 행동을 조회한다. 후보 확보 방식과 관계를 통한 근거 확인을 구분한다.

각 레코드에는 실제 action_id, document_id, chunk_id, 행동과 조건·기한·강도, 가능한 경우 단계·순서, 역할/관계 basis, 개념 ID를 보존한다. 역할/basis를 같은 맵으로 수집하고, 여러 OPTIONAL MATCH 때문에 행이 곱해지지 않게 한다. 여러 근거 청크를 가진 행동을 무조건 하나만 남기지 않는다.

문서 비교는 오늘 완성 Action Tool에 전부 넣지 않는다. 기존 compare_action_sources의 입력·반환·원문 경로를 CrossDoc 담당자에게 전달할 수 있게 정리한다. 초기에 기존 Graph 래퍼가 비교를 처리하더라도 메인의 정식 CrossDoc 라우팅과 인터페이스를 혼동하지 않는다.

모든 추가 조회에 allowed를 적용한다. ‘검색된 노드의 이름’을 근거 대신 쓰지 않고 실제 text/pdf_page/printed_page/Document 판본까지 확인한다.

**검증:** 학교 역할 질문에서 실제 SchoolAction→DONE_BY→SchoolRole, SchoolAction→SUPPORTED_BY→Chunk가 조회되며 해당 Chunk의 문서가 허용 범위에 있다. 빈 결과와 DB 오류를 구분한다.

## B05. Finding·Citation·GraphPath 직렬화

**참고:** D02 출처 formatter, D07 ref_path/Action Tool, D08 검증.

**제안 인터페이스:** `records_to_tool_result(records, tool_input, unresolved)` → ToolResult.

Finding은 원자적 주장이고 최소 한 Citation을 참조한다. 문서별 담당·조건·기한·강도가 다르면 나눈다. 예시 역할은 예시로, 모의훈련 표만 근거이면 그 성격을 유지한다. 청크 문구가 존재한다는 이유만으로 법적 의무·현재 적용 가능성을 확정하지 않는다.

Citation은 실제 조회한 문서·청크·뷰어 페이지와 원문 발췌로 만든다. 같은 chunk_id의 Citation은 한 번만 반환하며, 여러 Finding을 지지할 수 있는 발췌 범위를 확인한다. 이름·쪽수를 모델이 새로 작성하게 하지 않는다.

GraphPath는 실제 반환 레코드/Neo4j Path의 관계로 만든다. edge는 source_ref/relationship_type/target_ref이고 저장 방향을 보존한다. 조회되지 않은 DONE_BY/INSTANCE_OF 등을 보기 좋은 그림을 위해 만들지 않는다. 여러 갈래의 근거 연결이 담겨도 각 edge의 실재성과 소속을 검사한다. 반환 필요가 없는 Tool은 graph_paths=[]이다.

ToolResult의 OK는 **그 Tool의 task**가 충분한 근거를 가졌을 때다. 일부 역할·작업이 빠졌다면 PARTIAL, 확인할 주장 없음은 NO_EVIDENCE, 실행/검증 실패는 ERROR다. 오류/근거없음에서는 findings와 citations를 비우고 사유를 남긴다.

**검증:** 가짜 ID·뒤집힌 관계·누락 Citation·다른 문서의 근거·수신자 오귀속이 결과를 통과하지 못한다. 경로는 Citation을 대체하지 않는다.

## B06. Tool 실행 후 구조/DB/원문 검증 경계

**참고:** D01 수업 check, D05 실제 키 대조, D08 fixture validator. 기존 `verify_against_db()`를 적용 가능 범위에서 재사용한다.

구조 검사는 ToolResult 전체 키/타입, 호출 tool_name, 허용 문서, 페이지, Finding→Citation, 상태별 규칙을 확인한다. DB 검사는 HAS_CHUNK 문서 소속, 실제 text/페이지, SUPPORTED_BY, 표준 사전 ID, GraphPath의 실제 끝점·관계·방향을 확인한다.

기존 verify_against_db는 GraphPath 검사와 일반적인 역할/개념 연결의 진위까지 완성하지 않았으므로 별도 대조가 필요하다. GraphPath에 들어온 다른 문서/청크/행동도 allowed 범위에 속하는지 검사한다. 예상되는 관계라서 생략하지 말고 실제 MATCH 결과로 판정한다.

유종혁의 공통 validator와 연결할 때 개인 검사와 중복·차이를 정리한다. verify_db=False 같은 fixture 전용 우회를 실제 서비스 성공 경로로 사용하지 않는다. DB 대조 실패 주장은 제거/격리하고, 조작된 결과를 새 표현으로 바꾸어 다시 정상 통과시키지 않는다. 남은 검증 사실이 있으면 PARTIAL, 없고 실행 실패면 ERROR 등 원인을 보존한다.

**증빙:** 검사 전후 결과, 제외한 Finding과 사유, 질의와 실제 반환 관계, 원문 대조. 인용 포함 검사만으로 의미 해석 완료라고 주장하지 않는다.

## B07. 메인 입력·범위·의도·Tool 선택

**참고:** D04 route/StateGraph, D06 계약, D09 실제 LangGraph 예시.

**제안 노드:** normalize_input→classify_scope→classify_intent→select_tool.

메인은 QueryInput을 검증하고 원래 question을 보존한다. QueryInput의 task는 힌트이며, 각 Tool로 보내는 task는 메인이 구체화한다. MainState는 메인 내부 메모리이고 Tool이 직접 공유·수정하는 전역 State가 아니다.

권장 첫 Tool은 질병 사실→disease_search, 학교 행동/역할→action_search, 신고·법령→legal_search, 같은 개념의 문서별 비교→crossdoc_graph_search다. 병명 없음은 GENERAL이 아니다. 인사·사용법만 제한된 일반 안내로 종료하고, 미지원 질병/진단 확정/법적 자동 확정은 지원 범위 안내로 종료한다.

의도 분류가 애매하면 제한된 추가 설명이나 확인 필요를 표시한다. 단순 키워드 한두 개의 fixture 규칙을 운영 분류기라고 사용하지 않는다. ‘몇 일’이 있다고 count/Text2Cypher로 보내지 않는다. Tool을 네 개 모두 병렬 호출하는 것을 기본값으로 삼지 않는다.

**Tool registry 제안:** 승인된 네 이름→실제 callable을 매핑하고 deps를 주입한다. Tool은 일반 Python 함수여도 된다. @tool/bind_tools는 필요할 때 사용하는 래퍼이며 협업 계약을 대체하지 않는다.

**검증:** T02 병명 없는 학교 질문이 Action으로 가고 일반 인사는 0회 호출한다. 아직 없는 CrossDoc callable은 등록되지 않았음을 알리고, action_search를 CrossDoc인 척 호출하지 않는다.

## B08. 한 Tool 실행·최종 응답·호출 이력

**참고:** D04 ask_agent의 호출 추적, D09 ref_main_graph/ref_run. 수업 코드는 메시지 최종 문자열을 반환했지만 프로젝트는 계약 봉투가 필요하다.

execute_tool은 ToolInput 생성→callable 실행→ToolResult 검증→결과와 로그 저장을 수행한다. 실제 시도한 호출마다 tools_used를 순서대로 추가하고 search_rounds를 1 증가시킨다. 실패 호출도 기록한다. 미등록 Tool은 실행되지 않았으므로 연결 오류와 0회 호출을 구분한다. request_id는 로그 상관관계에 쓰고 질문·개인정보를 불필요하게 저장하지 않는다.

오늘은 1-Tool 경로를 실행하고 기본 충분성 판정 후 종료한다. 원질문의 일부만 처리했다면 PARTIAL, 확인 사실 없음은 INSUFFICIENT_EVIDENCE, 복구 불가 실행 오류이고 검증 사실 없음은 ERROR다. Tool OK를 원질문 전체 ANSWERED로 무조건 바꾸지 않는다.

최종 QueryOutput의 필드는 response_type/status/answer/findings/citations/action_ids/warnings/tools_used/search_rounds다. action_ids는 Finding들의 중복 제거 합집합이다. GraphPath는 ToolResult·내부 실행 로그·시각화에 남기며 최종 봉투에 새 필드로 추가하지 않는다.

서비스/노트북 공개 진입점은 입력 검사→compiled main graph.invoke→최종 결과 투영→v2 출력 검사 순으로 구성한다. 내부 State 전체가 응답으로 나가지 않게 한다. GENERAL/OUT_OF_SCOPE는 Tool과 원문 근거 없이 각각 안내 정책대로 종료하며, 전문 사실을 일반 모델 상식으로 보충하지 않는다.

**내일을 위한 연결점:** tool_results, unresolved, 예산과 마지막 호출 조건을 State에 둘 수 있지만 검증되지 않은 자동 루프는 오늘 완료로 보고하지 않는다. 내일 동일 입력 반복 방지·총 3회 한도·추가할 Tool 없음·복구 불가 오류 종료를 명시적으로 구현한다. recursion_limit만으로 Tool 3회 제한을 충족했다고 하지 않는다.

## B09. 실제 질문·오류 회귀 검증

**참고:** D10. 다음 fixture 성공과 실제 DB 성공을 별도 기록한다.

| 검사 | 오늘 확인할 것 |

| Action 단독 | 병명 없는 학교 행동 질문, 실제 역할·원문 경로와 ToolResult |

## B10. 실행 노트북과 팀 인수 자료

개인 `notebooks/school/`에 영문 파일명의 실행 노트북을 만들고 기존 학습 노트북은 참고 자료로 유지한다. 예를 들어 school_action_tool.ipynb에 Action 단독/근거 검증, school_main_tool_call.ipynb에 메인 1회 호출과 분기/실패 검증을 둘 수 있다. 현재 존재 여부를 확인하고 파일명을 확정한다.

증빙 JSONL/질의 로그는 Git 제외 개인 interim에 두고, 재실행 코드·검증 샘플·골든 질문은 팀 규칙의 개인 경로에 둔다. 커밋/푸시 전에 실제 변경 범위를 확인한다. 미커밋 사용자 작업을 임의로 되돌리거나 공동 경로를 자동 변경하지 않는다.

팀 인수 자료에는 다음을 명시한다.

1. 실제 callable의 import 경로·함수 형태·deps 소유권.
2. ToolInput/ToolResult 예시와 실행한 질문·검증 상태.
3. 실제 DB 스키마/인덱스 지원 범위와 부족한 데이터.
4. 실제 Cypher·GraphPath·PDF Citation 확인 결과.
5. 다음 Tool이 확인해야 할 미해결 작업과 경고.
