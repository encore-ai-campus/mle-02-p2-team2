## 2. 설계 원칙

1. **LLM이 하는 일과 코드가 하는 일을 나눈다.**
   - LLM은 검색된 청크를 근거로 **원자적 주장 + `chunk_ids`** 만 구조화해서 낸다.
   - 코드는 ① 반환된 ID가 검색 후보에 속하고 허용 문서(`allowed_document_ids`)에 속하는지 확인한 뒤 ② DB의 문서 ID·PDF 쪽수·원문으로 `Citation`을 만든다. 같은 청크의 `Citation`은 한 번만 반환한다.
   - 발췌문이 청크에 실제로 있는지와 DB 연결을 검사한다.
   - **그래도 주장·주체·의무 강도·조건이 원문과 맞는지는 사람이 PDF와 대조한다.** (코드가 만든 `Citation`이 올바른 쪽수를 가리키는 것과 주장이 맞는 것은 별개다.)
   - 유효한 근거가 없으면 주장하지 않는다.
2. **그래프는 단순하게 시작한다.** 노드 5~6개로 끝까지 돌리고, 검색 방식은 나중에 바꾼다.
3. **11/4까지는 "작게라도 끝까지".** 홍역 지침 + 감염병예방법 일부 쪽으로 T3을 통과시킨 뒤 문서를 넓힌다.
4. **공통 파일을 기다리지 않는다.** `contracts.py`·`validation.py`·`ids.py`는 내 폴더에 임시 복사본을 두고, 공통 파일이 병합되면 **차이를 확인한 뒤 import를 바꾼다.** (지시서 §5)
5. **신고·보고·통보를 섞지 않는다.** 법적 의미가 다른 내용은 별도 `Finding`으로 낸다. T3의 핵심은 **의료기관 신고를 학교 행동으로 잘못 매핑하지 않는 것**이다.
6. **공통 DB는 승인된 것만.** 제약조건·인덱스·ID 사전은 테스트 DB에서 먼저 실험하고, 공통 DB 적용은 나머지 두 사람의 승인 후에 한다. 확정되지 않은 임시 ID는 공통 DB에 적재하지 않는다.

### P5. 검색 + `Finding` 생성 + 검증 — 11/3~11/4  (이전 P5·P6 통합)
- 목표: 질문 → 청크 검색 → 주장 생성 → `Citation` 구성 → 검증 → `QueryOutput` 까지 **끝까지** 연결한다.
- 11/3: 실제 문서로 만든 **샘플 `QueryOutput`을 반환하는 `run()`**을 먼저 완성한다(검색·LLM 없이 고정 데이터).
- 구조:
  ```text
  validate_input → retrieve_chunks ─(결과 없음/관련성 부족)→ INSUFFICIENT_EVIDENCE ─┐
                                   └(근거 있음)→ compose_findings → build_citations ─┤
                                                                                      └→ verify_output → END
  ```
  - 내부 State에는 입력·검색 청크·생성 결과·오류를 담는다. 근거 부족 분기와 주장 생성 분기는 각각 **완전한 `QueryOutput`** 을 만든 뒤 출력 검증을 거쳐 끝난다.
  - 공개 함수는 동기 `run(query, *, deps=None)`. 실행 전 입력 검사, 실행 후 `validate_query_output(result, query)` 호출. 조회 실패는 근거 부족으로 숨기지 않고 `ERROR`로 처리한다.
  - 가짜 DB·LLM을 주입해 계약을 테스트한다.
- **검색 (첫 통과는 fulltext 중심, 벡터는 보류):**
  - 확인된 분석기 중 한국어에는 **`cjk`(2글자 단위)** 가 가장 가깝다. `standard`와 `cjk`로 **같은 질문의 결과를 비교**한다. 인덱스는 만든 뒤 `ONLINE` 상태인지 확인한다.
  - **개발용 질문(약 20개)으로만** **Hit@5·MRR을 측정해 기록**한다(수업의 평가 방식). 먼저 현재 수치를 남기고, 분석기·검색어를 바꾸면서 비교한다. 목표 수치는 측정 후에 정한다. **평가용 질문(약 10개)은 이 단계에서 보지 않는다.**
  - 정답 쪽을 알고 있는 질문(Q01, Q07, Q09, Q18 등)은 **상위 검색 청크를 직접 눈으로 확인**한다.
  - 검색어는 핵심어와 동의어를 쓰고 Lucene 특수문자를 처리한다.
  - `allowed_document_ids`로 먼저 범위를 제한하고, 그 안에서 `preferred_document_ids`를 우선한다. `allowed_document_ids=[]`는 "허용 문서 없음"이다.
  - fulltext가 놓치면 허용 문서 안의 **단순 키워드 포함 검색**을 임시 보조로 비교할 수 있다. (질문별 정답 청크를 코드에 고정하는 것은 검증이 아니다.)
  - **임베딩 벡터·hybrid 검색은 T3·통합이 안정된 뒤, 개발용 질문에서 실제 검색 실패 사례가 나올 때 비교를 시작한다.** 그때 임베딩 생성 방식과 `neo4j-graphrag` 추가 여부를 결정한다.

- `Finding` 규칙: ① 검색된 청크 ID만 인용 ② 신고·보고·통보·의료기관 신고는 별도 `Finding` ③ 근거가 없으면 주장하지 않음.
